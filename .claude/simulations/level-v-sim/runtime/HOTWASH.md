# Level V Simulation — Hotwash (v4-adapted)

**Run:** 2026-06-19 · **App:** FieldShore v4.0.0-slice.1 (v4-redesign) · **Scenario:** Verplanck Residential (car into 2-story wood-frame, single engine company, 3 shore points, 1 OP, 2h)

**Method:** live UI drive (single driver = conductor + 4 participants) + 14-agent analysis fan-out (3 moderator lenses + 4 persona AARs, each verified against source; adversarial verification of every candidate pitfall; synthesis).


## Verdict

The Level V baseline held. At the smallest scale — one engine company, one interim IC, 4 crew, 3 shore points, a single 2-hour operational period — FieldShore v4.0.0-slice.1 ran the full operational arc cleanly end to end: start operation, add shore point with correct ft/in+eighths measurement math, recommend struts against live per-rig inventory, deploy with atomic per-truck stock decrement, advance through the entire lifecycle (Strut Set → Cutting Station → Runner → Wood Shore Secured → Strut Equipment Returned), and end/archive the operation with a re-openable record. The safety engine — the part that actually matters for a structures specialist — is the strongest thing here: the over-capacity gate hard-closes the deploy path with no override, the unrated zone (>16 ft LongShore) demands a per-card acknowledgment and never prints a false capacity, and the conservative-floor lookup provably never over-reports buckling-governed load. No data-integrity defect surfaced: over-return is structurally impossible and the event-sourced log makes end-of-op and re-open non-destructive. This is an honest Phase-I slice, so the gaps are real but expected: the Command tab (org chart / situational status / PAR) is an unbuilt stub, the hazard log is unbuilt, and cloud sync is a deliberate local-only stub. The only verified defects are low-severity copy/affordance friction — chiefly a blank load rendering as "0 lbs" — plus one phone-specific command-picture friction (the at-a-glance status count strip is hidden below tablet width) that bites the lone IC. Nothing blocks the slice; the baseline test passed.


## Pearls (12)

- Safety engine refuses to over-report: between two datasheet rows the load lookup returns the longer (lower-capacity) row, never a linear blend — the single most important property of a strut selector, with the two historical over-report points (ACME 130″, LongShore 150″) pinned by tests and tables.test.ts independently re-transcribing every PDF value (engine.ts:88-93; tables.ts:11-18; engine.test.ts:16-24).
- Over-capacity gate closes the deploy path outright with no override: 30″ + 100,000 lb correctly yields a single 'Over capacity' card naming the 4-strut ceiling (ceil(100000/22000)=5 > 4), Deploy hard-disabled, no acknowledge escape hatch (engine.ts:218-234,310-329; RecommendationCard.tsx:147,250).
- Unrated zone (>16 ft LongShore) surfaces a per-card acknowledgment and never prints a false capacity: 200″ drives every card to capacity 0, suppresses the rated-capacity footer, and unlocks Deploy only on a per-card checkbox; the warning persists after ack and points to rescue engineering (engine.ts:213,237-245,297-299; RecommendationCard.tsx:138-139,148; WarningGate.tsx:14-20).
- Inventory integrity is structurally enforced: applyReturnTxn caps the restore with Math.min(available+1, quantity) so over-return is impossible, the deploy decrement aborts if available<=0, and the stock move + event-log append share ONE serialized Dexie transaction so stock and log cannot diverge (inventoryStore.ts:279-285; operationStore.ts:91-99,132-160).
- Event-sourced log with op-scoped projection makes End and Re-open non-destructive: OperationEnded never deletes data — activeOpId() simply stops counting the op, leaving it fully re-projectable for the archive drill-in and ADR-036 re-open; an accidental End is recoverable (projection.ts:11-18,55-73; reducer.ts:94-102).
- Two-tap clean deploy with honest partial-success and per-piece source confirm: a single-rig assembly deploys in 2 taps via one-tap commitBom when sourcing is 'complete'; cross-rig/missing-piece routes to a deliberate Review-sources step instead of a silent untracked deploy, and the one-step Add-SP path keeps an exhausted-stock group member Pending rather than failing the batch (AssignEquipmentSheet.tsx:132-138; AddShorePointModal.tsx:291-311).
- Return/step-back confirms name the exact piece AND source truck and distinguish reversible from terminal: Secured→Returned is a button raising a confirm worded 'the strut to Engine 1 … This cannot be undone', mid-lifecycle returns are reversible slides — removing the 'which truck?' ambiguity at the moment of action for a gloved operator (ShorePointCard.tsx:491-502; ReturnEquipmentModal.tsx:80-84).
- Gloved one-handed controls are field-right: advance/step-back are full-WIDTH slide tracks (the whole track is the drag surface, 56px floor / 60px Sunlight) with the next step spelled out in plain words, a 0.6 drag threshold + ghost-tap reset so a wet-screen smear commits nothing (Slider.tsx:11-13; primitives.css:729-745).
- Status identity is never color-only: every card shows the verbatim status WORD plus a colored stripe and a #N number tab that fills with the strut's system color once deployed, with documented WCAG contrast (default ≥6.16:1; dedicated Sunlight theme up to 10.31:1) for outdoor/gloved reading (Badge.tsx:36-42; tokens.css:117-126,197-208).
- Single deduction floored to the safe side, applied once at the engine boundary: effective length = floor((required − deductions) × 8)/8, subtracted exactly once and rounded DOWN (short strut absorbed by the wedge; long strut is the hazard), with the pre-save UI ledger using the same math as the engine so they never diverge — eliminating the v3-era double-deduction class (engine.ts:113-120; shorepoint/reducer.ts:73-75).
- Quick Find is correctly read-only and crew-safe: it runs catalog mode against the whole Paratech catalog with null inventory and a result card built with no deploy path, so a crew member can look up a strut without touching the live operation or department stock — the crew-vs-IC line drawn structurally, not by a label (QuickFind.tsx:69-72,139-143).
- Recoverable Pending-only delete: deleting a shore point asks first, is restricted to Pending, and is recoverable from a Deleted section (ADR-030) — a triple guard against accidental loss of incident data (observation log line 42).

### [LOW] Blank/optional estimated load renders as '· 0 lbs' on shore-point cards and Quick View
A load the operator left blank is correctly stored as undefined, but ShorePointCard.tsx:248 coerces it (`sp.estimatedLoad ?? 0`) and :288 unconditionally renders `· ${estLoad.toLocaleString()} lbs`, so an un-entered load reads '· 0 lbs' on the card a crew reads at a glance. '0 lbs' implies a measured no-load condition rather than 'not entered'. The same coercion repeats in the read-only Quick View drawer (ShorePointDetail.tsx:120,205), so the fix should cover both sites. Bounded risk: load never loosens a safety gate (the engine only consults estimatedLoad when >0, engine.ts:219; which strut fits is load-independent) and Quick Find already uses correct copy ('Leave blank if unknown — load doesn't change which strut fits', QuickFind.tsx:114) — so this is misleading copy, not a math error, and an inconsistency with the app's own better framing. Notably the SAME detail line already conditionally omits the deduction segment (ShorePointCard.tsx:281-287) — the omit-when-absent pattern exists right next to the load segment and just wasn't applied to it. Caveat: card.md:123,127 actually specifies the '· 0 lbs' literal, so the spec also needs a one-line amendment. Fix: render '—' or drop the load segment when estimatedLoad is undefined, at both ShorePointCard.tsx:288 and ShorePointDetail.tsx:205.


### [LOW] Shore type silently defaults to T-Shore with no cue distinguishing system-default from operator choice
The shore-type default is REAL and intentional (AddShorePointModal.tsx:85 seeds 't-shore'; line 119 first-point default; carry-over from the last point otherwise) — so a saved card reading T-Shore when the operator never touched the control is the default firing, not a logic bug. The friction is purely presentational: the controlled InlineSegmented always renders exactly one option highlighted with no unset/no-selection visual state, so the UI cannot distinguish 'system pre-selected this' from 'operator chose this'. Because shore type drives the wood/deduction math and (for Double-T/3-Post) the strut count, an unnoticed default could carry the wrong geometry into a deploy. Stays low: the default is the most common single-strut config, is fully visible the whole time, is one tap to change, and the resulting strut count is echoed back in the qty helper. The 3-Post auto-wood behavior is correct per the v3.9.1 lesson (only 3-Post auto-fills 6x6). This is an affordance/design note (e.g. a subtle 'default' hint), not necessarily a code change.


### [MEDIUM] No at-a-glance incident status total on the phone — the per-status count summary strip is hidden below tablet width
Persona-sourced (IC, Capt. Torres) and grounded in cited source: the StatusSummaryBar component exists and works (OperationsBoard.tsx:128) but a deliberate design call (G-15) suppresses it below tablet width via a 768px media query (operations.css:161-163 vs the gate at 1274), so on an actual phone there is no single-line '3 points · 1 pending · 1 cutting · 1 secured' read — the lone IC must eyeball seven collapsible lane headers to total the incident. This is friction, not a GAP: the code is built and works; only a width gate hides it. It bites precisely the one person who is always on a phone and most needs the total. Tolerable at 3 shore points; would not scale. Suggested fix: show the summary (compact) at all widths, or surface a one-line incident total in the Operations header next to the op name. Honest caveat: this finding comes from the IC AAR's CSS citations and was not independently re-verified line-by-line in the moderator pass — confirm operations.css:161-163/1274 before acting. Severity capped at medium and bounded to the lone-IC-on-phone case.


### [LOW] Command nav tab dead-ends on an unbuilt stub instead of pointing the IC to the de-facto command picture
Distinct from the deliberate Command/org-chart GAP itself: the issue is that tapping a primary nav item returns a bare 'Command isn't built yet' EmptyState (command.tsx:4-12), which reads to an IC like the app failed — even though the situational data they wanted (the Operations board, the de-facto SitStat) is one tab over. The unbuilt org chart is correctly a GAP (#323); this is a small wayfinding refinement on top of it: while Command is unbuilt, either route the tab to the Operations board or relabel the stub to point there ('Command picture lives on the Operations board for now'). Low severity, cosmetic copy/routing change; the underlying capability gap is tracked separately.

## Persona After-Action Reviews


### IC (Capt. Torres) — sole incident commander, Millbrook Engine 1, Verplanck Residential (Level V)
- **Intent:** As the only officer on a single-company response, I am the incident. I needed the app to do three things for me end-to-end: stand up the operation fast, give me a command picture — overall status of all 3 shore points at a glance without working the radio or walking the building — and close the incident cleanly with a clear record of where my gear ended up. At Level V I'm not delegating; I personally create the op, watch it, and end it, all from a phone clipped to my coat.
- **Actual:** Two of the three worked cleanly; the middle one — the actual command picture — was a split result. Create was a Pearl: the Start Operation modal gated on a name ("Enter an operation name" disables the button, StartOperationModal.tsx:33,98), took an optional address, and fired one clean OperationCreated event (StartOperationModal.tsx:68). End was a Pearl: End Operation confirmed, archived under "Past operations," was re-openable, and — best part — warned me that gear was still up and which rig was left short for the next call (OperationsBoard.tsx:790-805,1284). That is exactly the accountability an IC needs at handoff. The command picture itself: the Operations board IS my SitStat — op name up top, 7 status lanes each with a live count badge, an inventory companion (OperationsBoard.tsx:1119,1261). For 3 shore points that's genuinely workable. But two things bit me. First, the dedicated Command tab in my bottom nav — the place I instinctively went for "show me the incident" — is a dead-end stub reading "Command isn't built yet" (command.tsx:4-12); I tapped it, got nothing, and had to back out to Operations. Second, the one true at-a-glance strip — the per-status count summary across the top — is hidden on a phone; it only switches on at tablet width (operations.css:161-163 vs the 768px media query at 1274). So on my actual device I had no single-line "3 points: 1 pending, 1 cutting, 1 secured" read — I had to eyeball seven collapsible lane headers to total it up myself.
- **Why any gap:** The difference traces to where the design put the command picture versus where an IC's hand goes looking for it. The board was built first and carries the real situational data; the Command tab and org chart are a deliberately deferred Phase-I block (#323), so the stub is a GAP, not a defect. The hidden summary strip is a genuine friction, not a GAP: the code exists and works (StatusSummaryBar, OperationsBoard.tsx:128) but a design call (G-15, commented "phone does not show it") suppresses it below tablet — reasoning that a phone is space-tight. That's the wrong call for the lone IC, because the lone IC is the one person who is ALWAYS on a phone and who most needs the total. The two real Pearls (create, end-with-rig-warning) landed because they're single, linear, well-instrumented flows. The command picture is harder precisely because it's the synthesis step, and at Level V the synthesis is small enough that the board mostly carries it — masking the gap that a bigger incident would expose.
- **Do differently:** Two concrete changes. (1) Stop hiding the status-summary count strip on phones — show it (compact) at all widths, or at minimum surface a one-line incident total in the Operations header next to the op name ("3 points · 1 pending · 1 cutting · 1 secured"). The lone IC lives on a phone; the glance view should follow the smallest device, not abandon it. This is a small CSS change (drop or invert the 768px gate at operations.css:1274) for a real command-picture win. (2) The Command tab in the bottom nav should not dead-end while it's unbuilt — either route it to the Operations board (the de-facto SitStat) so the instinctive "show me the incident" tap lands somewhere useful, or relabel the stub to point me there ("Command picture lives on the Operations board for now"). Tapping a primary nav item and getting "not built yet" reads, to an IC, like the app failed — even though the data I wanted was one tab over. Keep create and end exactly as they are; the end-of-op rig-shortage warning in particular is a model of field-right accountability and should be preserved verbatim.
- **Top friction:** No at-a-glance command picture on the phone: the per-status count summary is display:none below tablet width (operations.css:161-163 / 1274), and the Command nav tab dead-ends on an unbuilt stub (command.tsx:4-12) — so the lone IC, who is always on a phone, has to manually tally seven lane headers to know overall incident status. (Tolerable at 3 shore points; would not scale.)

### Shoring (FF-1)
- **Intent:** My whole job at Verplanck was the core loop: take a measured opening, find the strut that fits and is actually on our rig, deploy it, then walk the shore through cutting and set. With 4 crew and 3 shore points on a single engine, I needed the app to be a fast, dumb tool — measure, get a ranked answer, tap deploy, advance. I expected to find AND deploy the right strut from Quick Find (the calculator), and I expected the load number I entered to matter.
- **Actual:** The loop was fast and clean, and one of my expectations was deliberately corrected by the app. Creating a shore point gave me ft/in + eighths measurement that correctly produced "Required strut length 30″" (log E+0:04→0:30; verified MeasurementInput + effectiveLengthFrom). Find Available Struts returned 4 ranked cards each naming the SOURCE RIG, the deduction ledger, capacity-at-length, and a planning-aid disclaimer — including an AT 19-25 with a cross-rig 6″ extension (strut on Engine 1, extension on Rescue 2). Deploy decremented the right truck's count (Engine 1 AT 25-36 went 2→1→0 across two deploys) as one atomic transaction, and surfaced "deployed X of N" rather than a silent success when stock would run out (AddShorePointModal.tsx:290-309). Advancing through Strut Set → Cutting Station → Runner → Wood Shore Secured → Strut Equipment Returned worked, with the card's headline length re-labeling itself "Required strut length" → "Cut length" → "Set length" as I moved through phases (ShorePointCard.tsx:54-62). On the SAFETY side it shone: 30″ at 100,000 lb correctly killed Deploy with an "Over capacity" badge and no override; 200″ surfaced an "Unrated" zone with a per-card acknowledgment checkbox before Deploy unlocked; 16″ gave a plain "No matching struts" with no false deploy. My one wrong expectation: Quick Find does NOT deploy — it's a read-only calculator (no onDeploy passed, QuickFind.tsx:139-143). Deploy lives in Operations. The topFriction was a small one: on a card with no load entered, the detail line printed "0 lbs" instead of leaving it blank (ShorePointCard.tsx:248,288 — estLoad = sp.estimatedLoad ?? 0).
- **Why any gap:** The loop felt fast because the app is honest about the two things a shoring FF actually fears: deploying off-book equipment we don't have, and trusting a strut beyond its rating. The recommendation engine sources against LIVE rig inventory, not the whole catalog, so what I see is what I can grab — and the per-rig BOM (ADR-033) means even a cross-truck extension is spelled out, not hidden. The safety gates aren't warnings I can click past — over-capacity closes the deploy path outright and unrated demands an explicit per-card acknowledgment (RecommendationCard.tsx:147-148,239-244). The Quick-Find-can't-deploy "miss" was actually correct design: the calculator is a pre-arrival/no-op lookup with no rig context, so deploying from it would be deploying from nothing. The "0 lbs" friction is just a copy default — the code coalesces a blank load to the number zero for display, which reads as "I measured the load and it's zero" rather than "load unknown." Quick Find itself gets this right with better copy ("Leave blank if unknown — load doesn't change which strut fits", QuickFind.tsx:114), so the two screens disagree on how they phrase the same blank.
- **Do differently:** Keep the loop exactly as-is — finding and deploying the right strut was fast, clear, and safe; this is the app working. Two concrete fixes, both small: (1) On the deployed/pending card, render a blank load as "—" or omit the segment entirely, the way Quick Find already handles it — "0 lbs" is a false reading on a card a structures specialist will trust (ShorePointCard.tsx:288). (2) Consider a quiet bridge from Quick Find to Operations: as Shoring I'll often calculate an opening before the op is even named, and right now I have to re-enter the measurement in Add Shore Point. A "use this in an operation" hand-off would close the one seam in the loop. Neither blocks shipping; the core loop passed the baseline-scale test cleanly.
- **Top friction:** Blank estimated-load renders as "0 lbs" on the shore-point card (ShorePointCard.tsx:248,288) instead of "—"/omitted — a false "load is zero" reading where Quick Find already shows the correct "leave blank if unknown" framing. Minor copy/semantics defect, not a loop-breaker.

### Entry (FF-2) — crew-level firefighter, new to FieldShore, used Quick Find independently to look up a strut for a measurement
- **Intent:** My job on this incident: I had a raw opening measurement in hand (2'6" / 30") and I needed to know, on my own, which Paratech strut would span it — without bothering the Captain (IC) and without touching the operation he was building. I'm new to this app. I expected to find a self-serve calculator, punch in my number, and get an answer I could trust as a planning reference, the same way the v3 app let anyone "Quick Find" a strut.
- **Actual:** It worked, and the read-only line is drawn exactly right. I tapped the clearly-labeled "Quick Find" tab (magnifier icon) in the bottom nav, landed on a measurement field, entered 2'6", and hit "Find Struts." A results sheet rose up (ADR-031, src/ui/quickfind/QuickFind.tsx:133) listing every catalog strut that fits — LS 203 (22,000 lb), AT 25-36 (20,000 lb), AT 19-25 — each with its required-length math and a permanent planning-aid disclaimer. Crucially for a crew member: NO Deploy button, NO source-rig, NO inventory pull (RecommendationCard omits onDeploy/source/location in Quick Find mode — RecommendationCard.tsx:246, QuickFind passes inventory=null at QuickFind.tsx:72). That is the crew-vs-IC line drawn in the right place: I can look up all day, but committing equipment to the op stays an Operations/IC action. PEARL: the optional load field even carries plain-language helper text — "Leave blank if unknown — load doesn't change which strut fits" (QuickFind.tsx:114) — which is better copy than the deployed card's "0 lbs." Two snags as a true first-timer: (1) the screen has no on-screen title or one-line "this is the strut calculator" statement — the header just reads the brand lockup "FieldShore" (AppHeader.tsx:7), so the only place the words "Quick Find" appear is the tab I tapped; the screen drops me straight into a measurement field and I infer the rest from field labels. (2) There IS a genuinely excellent built-in tutorial for this exact screen (QUICK_FIND_TOUR in tours.ts:19 — it even spells out "Nothing here is saved towards an operation... or assigned from department inventory"), but it does NOT auto-fire for a guest/new user; it only runs on deliberate account creation or a Settings replay (OnboardingHost.tsx:14,28), and the app's cold-open redirects to /operations, not here (router.tsx:67-69). So the one piece of content that would have answered every new-user question never appeared for me.
- **Why any gap:** The crew-vs-IC differentiation is solid because it's enforced structurally, not by a label: Quick Find runs in catalog mode with null inventory and the result card is built without a deploy path, so there's literally nothing for a crew member to accidentally commit. The self-explanatory gap is a sequencing/trigger mismatch, not missing content. The team clearly wrote crew-grade onboarding for exactly this screen and exactly my situation, but gated it behind account creation — which a guest firefighter who just wants to check a number never does. The guest-first design (ADR-015, app fully usable without signing in) is the right call, but it has the side effect that the best explanatory content is invisible to the very person it was written for. The bare-screen-into-a-field pattern leans on field labels being self-evident, which they nearly are for a strut tech, but the screen-level "what is this" is carried only by the tab name, which disappears the moment you're on the screen.
- **Do differently:** Two small fixes, no redesign. (1) Make the Quick Find tour (or at least a one-line intro coachmark) available to guests too — let a new user tap a "?" or have the first-ever visit offer the tip, instead of locking it behind account creation. The content already exists and is excellent; it just needs a guest trigger. (2) Give the screen a quiet one-line purpose statement at the top — something like "Strut calculator — look up what fits a measurement (nothing is saved or assigned)." That single line closes the self-explanatory gap for a first-timer AND restates the crew-vs-IC boundary in plain sight, so a new crew member never wonders whether looking something up here touches the live operation. Keep everything else exactly as built — the read-only sheet, the no-deploy guarantee, and the load helper text are all Pearls worth protecting.
- **Top friction:** The screen is self-explanatory only if you already know it — the built-in Quick Find tutorial that explains everything (including that nothing is saved or assigned) never auto-fires for a new guest user, and the screen itself has no on-screen title or one-line purpose, so a first-timer is dropped into a bare measurement field and left to infer the rest.

### Runner (FF-3) — runs cut struts to the shore point, sets wood shore, returns spent equipment. Working a phone with gloves on.
- **Intent:** As the Runner I needed to push three shore points the back half of the lifecycle from a gloved hand on a phone: pull a cut strut out of the Cutting Station (Mark Cut Done -> Send to Runner), carry it and advance Runner -> Wood Shore Secured, then strike the strut and return each piece to its source truck. My ask of the app was simple and one-handed: the "what do I do next" control had to be big, obvious, fat-finger-proof against a wet/ghosty screen, and the return had to tell me which truck the strut goes back to so I don't dump it on the wrong rig.
- **Actual:** The flow held together cleanly end to end in the log (SP #1 ran Cutting Station -> Mark Cut Done -> Send to Runner -> Runner -> Wood Shore Secured -> Strut Equipment Returned, and Engine 1's AT 25-36 count climbed 1 -> 2 on the terminal reclaim). PEARL: the controls are full-WIDTH slide tracks, not a tiny knob — Slider.tsx:11-13 explicitly states the whole track is the drag surface "because gloved fingers miss a 36-44px knob," and primitives.css:729-745 puts the advance track at a 56px floor (60px in Sunlight), step-back at 48px, both above the 44pt thumb target. PEARL: each next step is spelled out in plain words on the track ("Slide to send to Runner," "Slide to set Wood Shore Secured," "Slide back to Cutting Station") — never an icon I'd have to guess at with gloves on. PEARL: the slide is deliberate by construction (1:1 drag past a 0.6 threshold, ghost-tap reset on every press-down, pointercancel on a vertical pan) so a wet-screen smear or a stray tap commits nothing — exactly the protection a Runner on a chaotic fireground wants. PEARL: the return is a clear two-tier model — Runner -> Secured is a reversible slide, but the final strike (Remove & Return Equipment) is a BUTTON that raises a confirm naming the exact piece and rig ("the strut to Engine 1") and warning "This cannot be undone" (ReturnEquipmentModal.tsx:80-84). It even speaks back "AT 25-36 returned to Engine 1" (OperationsBoard.tsx:611-612) so I get confirmation I returned to the right truck. The one thing the live drive did NOT actually exercise is the gloved SLIDE gesture itself: the headless desktop driver has a mouse, so per ADR-034/035 every slide swapped to a tap-once button (log line 22) — so the buttons were proven, the drag-with-gloves was reasoned-correct from the code but not driven.
- **Why any gap:** The difference between "verified working" and "verified gloved" comes from the test rig, not the app. The Slider branches on useHasMouse: a touch device gets the slide-only track (no button twin, ADR-026/KB-5), a mouse device gets a button instead. The live drive ran on a desktop driver with a mouse, so it correctly rendered and clicked buttons — meaning the gloved drag-past-threshold ergonomics (does a 0.6 threshold feel right through a structural glove? does pan-y reliably let me scroll the board without a stray commit?) are sound in the source but were not physically validated. That is a property of how this baseline sim was driven, not a defect. A second, smaller friction is real regardless of input: the Runner cannot reach a cutting card from the main board at all — the cutting card is read-only there and you must first tap the "Cutting Station" segmented sub-nav to get the Mark Cut Done / Send to Runner controls (OperationsBoard.tsx:984-997, CuttingStation gated by cuttingStation prop). That is by design (the cutter owns the station), but for a one-IC, 4-person company where the same gloved hand may be doing cutting AND running, it's an extra deliberate tap/context-switch to find where the "send to runner" control lives.
- **Do differently:** Two things. First, close the verification gap, not a code gap: drive the Cutting-Station-onward steps once on an actual touch target (a phone or touch-emulated viewport) so the gloved SLIDE — Send to Runner and Set Wood Shore Secured — is exercised as a real drag, confirming the 0.6 threshold and pan-y scroll behavior feel right through a glove. The code is built for it; it just was not driven that way in this run. Second, a small wayfinding nudge: when the only place to advance a cut strut is the Cutting Station sub-view, the Operations-board cutting card could carry a one-line hint ("Work this in Cutting Station ->") so a solo Runner/cutter on a single-company job isn't left wondering why the card looks frozen. Keep everything else exactly as is — the full-width tracks, the spelled-out next-step labels, the ghost-tap defense, the reversible-slide-vs-final-button split, and the return confirm that names the piece and the truck are all genuinely good and field-right for a gloved hand.
- **Top friction:** The gloved SLIDE gesture for cutting-onward (Send to Runner, Set Wood Shore Secured) was never physically driven — the desktop/mouse test rig swapped slides for tap buttons (ADR-034), so those advance controls were proven as buttons but the actual drag-with-gloves ergonomics the role hinges on are reasoned-correct from source, not validated. Not an app defect; a coverage gap in how this baseline run was driven.
