## Bugs for this release

### Bug 1: Cut measurement disappears after sent to runner
**Issue:** #29
**Symptom:** Once a shore point is sent to runner status, the cut length disappears from the card.
**Root Cause:** `renderShorePoints()` in `app.js` line ~1760 only shows cut length when `status === 'cutting'`:
```js
if (status === 'cutting' && sp.cutLength != null) {
  html += `<div class="cut-length-display">✂ Cut Length: ${sp.cutLength}"</div>`;
}
```
The runner/secured/returned statuses don't render it.
**Fix:** Change the condition to show cut length for cutting, runner, secured, and returned statuses:
```js
if (['cutting','runner','secured','returned'].includes(status) && sp.cutLength != null) {
```
Also show actualCutLength if it differs from cutLength (ties into #27).

### Bug 2: Actual cut should be main measurement, flag differences
**Issue:** #27
**Symptom:** When an actual cut measurement differs from the expected, there's no visual indication.
**Root Cause:** `renderCutTableCard()` at line ~2727 shows actualCutLength in a small orange text, but the main display at line ~2757 always shows `sp.cutLength`. On the operations card, neither actual nor expected is shown after cutting status.
**Fix:**
1. In `renderCutTableCard()` (cut table view), if `sp.actualCutLength` exists and differs from `sp.cutLength`, show a warning badge/highlight.
2. In `renderShorePoints()` (operations view), when showing the cut length display, prefer actualCutLength if it exists:
```js
const displayCut = sp.actualCutLength != null ? sp.actualCutLength : sp.cutLength;
const diffWarning = sp.actualCutLength != null && sp.actualCutLength !== sp.cutLength
  ? ` <span class="text-danger" style="font-size:11px">(expected: ${sp.cutLength}")</span>` : '';
html += `<div class="cut-length-display">✂ Cut: ${displayCut}"${diffWarning}</div>`;
```

### Bug 3: Label "from: apparatus" → "Equipment from:" / "Assigned to"
**Issue:** #30
**Symptom:** Shore point cards show "From: Engine 169" — should say "Equipment from:" and assigned apparatus should say "Assigned to".
**Root Cause:** `renderShorePoints()` line ~1745:
```js
`<span class="apparatus-source">From: ${getApparatusName(sp.deployedStrut.apparatus)}</span>`
```
**Fix:** Change "From:" to "Equipment from:":
```js
`<span class="apparatus-source">Equipment from: ${getApparatusName(sp.deployedStrut.apparatus)}</span>`
```
For external equipment, "External:" → "External equipment from:".
Note: "Assigned to" label — need to check if there's a separate assigned apparatus field or if this refers to the same concept. If the deployed strut's apparatus IS the assignment, then the label change is just the "From:" → "Equipment from:" fix.

### Bug 4: Runner card button order reversed
**Issue:** #31
**Symptom:** On the runner status card, "→ Secured" is on the left and "← Send Back" is on the right. Other cards have the forward action on the right.
**Root Cause:** `renderShorePoints()` line ~1782-1785:
```js
if (status === 'runner') {
  html += `<div class="action-row">
    <button ...>→ Secured</button>
    <button ...>← Send Back</button>
  </div>`;
}
```
Compare with cutting status (line ~1776) where "← Send Back" is the only button, and strutplaced (line ~1770) where "→ Cutting Table" is left and "← Send Back" is right. The pattern is inconsistent.
**Fix:** Swap the button order so "← Send Back" is on the left and "→ Secured" is on the right, matching the left-to-right progression pattern used on other cards:
```js
<button ...>← Send Back</button>
<button ...>→ Secured</button>
```

### Bug 5: Shore point cards missing at some hierarchy levels
**Issue:** #32
**Symptom:** When navigating the breadcrumb hierarchy, shore point cards don't appear at intermediate levels — you have to drill all the way down.
**Root Cause:** `renderDrilldownList()` at line ~2330. When a next drill level exists, it returns the drill-down group cards (not shore point cards). Shore point cards only render when `getNextDrillLevel()` returns null (no more levels). So at a Building level, if there are Division sub-groups, you only see the Division group tiles, not the shore point cards within.
**Fix:** After rendering drill-down group tiles, also render the shore point cards below them. In `renderOperations()`, after the drill-down list, always render the filtered shore points using `renderShorePoints()`:
```js
const drillHtml = renderDrilldownList(filteredPoints);
if (drillHtml) {
  spList.innerHTML = drillHtml + renderShorePoints(filteredPoints);
} else {
  spList.innerHTML = renderShorePoints(filteredPoints);
}
```
This shows the group tiles for navigation AND the shore point cards for context at every level.

### Bug 6: Plates not in inventory shouldn't be selectable
**Issue:** #28
**Symptom:** When selecting a top or bottom plate during operations, all 14 plate types are shown regardless of what's in inventory.
**Root Cause:** `openPlatePicker()` at line ~3415 shows all plates from `BASE_PLATES`. The plate picker grid is built in the HTML with all plates, not filtered by inventory.
**Fix:** When in operations context (shore point form inside an active operation), filter the plate grid to only show plates that are in the current operation's inventory. Add an inventory check:
```js
const opInv = getOperationInventory();
const availablePlates = opInv.filter(item => item.type === 'plate').map(item => item.plateId);
```
Then in the plate grid rendering, add a `disabled` class or hide plates not in `availablePlates`. Always keep "None" as an option. Note: the plate grid HTML is static in index.html — may need to rebuild it dynamically in `openPlatePicker()` or `openShorePointForm()`.
