# Plan: v3.11.0 — Field feedback fixes (7 items)

## Context

Seven in-app feedback entries from Hartsdale Fire (Alex's dept) spanning v3.8.2 → v3.10.1. Originally drafted as 3-item v3.11.0; expanded on 2026-05-17 after a fresh `/feedbackreview` pulled 4 more bugs from v3.10.0/v3.10.1, one of which (dark-mode contrast in numerous locations, #88) is the broader version of the existing #84.

All 7 items are bugs or UI-polish fixes — no new features. Versioned as v3.11.0 MINOR rather than v3.10.2 PATCH because of the cumulative breadth (multiple regressions + comprehensive dark-mode pass) and to leave room for a true PATCH later in the cycle.

## Implementation

### Workstream A — Bug #82: Unable to select top or bottom plate in Quick Find
**Issue:** [#82](https://github.com/Vergo402/paratech-struts/issues/82)
**Symptom:** Operator opens Quick Find, taps Top Plate or Bottom Plate picker, picker opens — but tapping a plate option does nothing (no selection, no close). Filed against v3.9.1.

**Investigate:**
- `openPlatePicker(pickerId)` at [app.js:5700](app.js#L5700) — moves the grid to `document.body` when inside a modal stacking context, but for Quick Find (no modal) the grid stays in its original parent.
- `selectPlate(pickerId, plateId)` at [app.js:5752](app.js#L5752) — handler called by `.plate-option` onclick.
- `closePlatePickers()` at [app.js:5688](app.js#L5688) — closes on scrim click, scrim registered at line 5734.
- Suspicion: `plateScrim` element at [app.js:5729-5736](app.js#L5729) sits on top of the in-place grid in Quick Find context. Tapping a plate hits the scrim first → `closePlatePickers` fires → tap never reaches `.plate-option`.
- Verify in DevTools: when Quick Find picker is open, inspect z-index stack of `plateScrim` vs the grid.

**Fix approach:** Either bump grid z-index above scrim, OR always move grid to `document.body` regardless of context (the SP-modal path already works this way). Option 2 is cleaner — single code path. Confirm Quick Find positioning still correct when moved to body.

**Verification:** Walkthrough on mobile + desktop preview — open Quick Find, tap top plate picker, tap an option, confirm picker closes and selected plate name appears on picker button. Console clean.

### Workstream B — Bug #83: FieldStruts header is locked at top
**Issue:** [#83](https://github.com/Vergo402/paratech-struts/issues/83)
**Symptom:** Blue "FieldStruts / Hartsdale Fire / v3.x.x" header occupies vertical space on every screen and doesn't scroll away. Eats real estate on small phones, especially in landscape.

**Investigate:**
- `.header` at [style.css:78](style.css#L78) is `flex-shrink: 0` inside `.app` flex column. Not `position: fixed` — but stays visible because scrolling happens inside `.screens` (child below it).
- Confirm actual scroll container in DevTools.

**Fix approach:** Operator ask was "needs to not be locked in place." Interpretations:
1. **Scroll-away** (literal): make `.header` scroll with content. Loses persistent dept-name display unless added elsewhere.
2. **Sticky-top with smaller padding** (middle ground): visible at the top of scroll, slimmer footprint.
3. **Collapse on scroll** (compromise): full height at top, collapses to slim bar when scrolled.

**Pre-decision needed from Alex** before implementing.

**Verification:** Walkthrough on mobile preview — scroll a long screen (Operations with many shore points), confirm header behavior matches choice. Test portrait + landscape.

### Workstream C — Dark-mode contrast pass (#84 + #88)
**Issues:** [#84](https://github.com/Vergo402/paratech-struts/issues/84), [#88](https://github.com/Vergo402/paratech-struts/issues/88)
**Symptom:** Dark backgrounds with dark text in multiple components. Specifically called out: plate picker names on desktop dark mode (#84). Broader report: "numerous locations" (#88).

**Investigate (known offenders from initial scan):**
- `.plate-option .plate-name` at [style.css:1096](style.css#L1096) — no `color` declaration, inherits, falls back wrong in dark mode
- `.quick-add-plate .plate-label` at [style.css:570](style.css#L570) — same issue
- `.plate-option` itself at [style.css:1073](style.css#L1073) — no color override
- `.btn-success` at [style.css:1309](style.css#L1309) — hardcoded `#2E7D32` (dark green), invisible on dark bg
- `:root[data-theme="dark"]` block at [style.css:1468-1580](style.css#L1468) — missing counterparts for the above

**Fix approach:**
1. Quick wins: add explicit `color: var(--text)` to `.plate-option`, `.plate-name`, `.plate-height`, `.quick-add-plate .plate-label`. Replace hardcoded `#2E7D32` with `var(--green)` (#66BB6A in dark) or theme-aware token.
2. Full audit pass: `grep -E "color:\s*#[0-9a-fA-F]{3,6}" style.css` — for each match, confirm it has a dark-mode override OR uses a theme variable. Flag and fix everything that fails.
3. Walk the app in dark mode in the preview (every tab, every modal) and screenshot anything illegible.

**Verification:** Walkthrough on desktop preview (tablet preset) in BOTH light and dark. Every tab visited. Every modal opened. Plate picker confirmed legible (≥ 4.5:1 contrast WCAG AA). Screenshot of dark mode for release notes.

### Workstream D — Bug #85: Can't edit / change length of pending shore points
**Issue:** [#85](https://github.com/Vergo402/paratech-struts/issues/85)
**Symptom:** Operator opens a pending SP card, edits required length, save appears to succeed but value doesn't actually update (or reverts).

**Investigate:**
- `editShorePoint()` at [app.js:5068-5120](app.js#L5068) — opens modal pre-populated with current values
- `confirmEditShorePoint()` at [app.js:5122-5156](app.js#L5122) — save handler
- Field name check: v3.5.2 fix S1 changed `findStrutCombinations` to receive `requiredLength` (raw) instead of `effectiveLength` (already deducted). Confirm edit writes back to `requiredLength`, not `effectiveLength`.
- Save → render sequencing: `firebaseSave()` at line ~5149 then `renderOperations()` at line ~5151. If render reads from a stale snapshot before the write commits, the change appears to revert.

**Fix approach:** Per v3.5.3 architecture, every mutation should be local-first + persist + then conditional Firebase sync via `firebaseSave()`. Confirm edit flow uses `persistOperation()` and writes both locally and to Firebase. Don't await Firebase before re-rendering (that breaks offline) — rely on the local-first model.

**Verification:** Walkthrough — create a pending SP with required length 60". Open edit, change to 75", save. Confirm: card shows 75", refresh page, still 75", check Firebase console, value persisted. Also test offline (devtools → offline) — same flow should work and queue.

### Workstream E — Bug #86: Quick-add inventory list jumps to top on plate image click
**Issue:** [#86](https://github.com/Vergo402/paratech-struts/issues/86)
**Symptom:** On Inventory tab → quick-add flow, clicking a plate's image (to increment count) causes the scroll position to reset to the top of the list every time. Painful when adding to plates at the bottom of a long list.

**Investigate:**
- `quickAdd()` at [app.js:2310-2344](app.js#L2310)
- `showAddEquipment()` at [app.js:2244-2308](app.js#L2244) — regenerates innerHTML of all grids on every call
- Line 2343 — `showAddEquipment()` is called after every successful `quickAdd()`, wiping scroll position
- Modal container needs `scrollTop` snapshot + restore around the re-render

**Fix approach:** Two options:
1. **Quick fix:** snapshot `modal.querySelector('.modal-content').scrollTop` before re-render, restore after.
2. **Better fix:** stop calling `showAddEquipment()` on every click. Instead, find the specific tile that changed and update only its count badge. Avoids the full re-render churn entirely.

Recommend (1) for v3.11.0 (minimal risk), file (2) as a follow-up cleanup if time permits.

**Verification:** Walkthrough — open Inventory → quick-add, scroll to a plate near the bottom, click its image to add 1, confirm scroll position stays put. Click again — still stays put. Test on mobile + desktop.

### Workstream F — Bug #87: Edit Apparatus modal shows both Add and Edit forms
**Issue:** [#87](https://github.com/Vergo402/paratech-struts/issues/87)
**Symptom:** When operator opens "Edit apparatus" from the apparatus list, the modal renders both the "Add new apparatus" form (at the top) AND the "Edit existing" form (below). Confusing — operator doesn't know which to use.

**Investigate:**
- `editApparatus(id)` at [app.js:1981-1998](app.js#L1981) — only replaces innerHTML of `#apparatusManageList`
- Modal at [index.html:317-342](index.html#L317) contains:
  - "Add new apparatus" form (lines 320-336): name input + type select + "Add" button
  - `#apparatusManageList` container (line 338): edit form rendered here
- The add form is never hidden when in edit mode

**Fix approach:**
1. Wrap the add form in `<div id="addApparatusForm">` (index.html:320-336).
2. In `editApparatus()`: hide it via `document.getElementById('addApparatusForm').style.display = 'none'`.
3. On `renderApparatusManageList()` (the default/non-edit view) OR on modal close: restore via `style.display = ''`.
4. Also clear add-form input values when entering edit mode so they don't carry over.

**Verification:** Walkthrough — Settings → Apparatus → Edit existing apparatus → confirm ONLY the edit form is visible. Cancel/save → confirm add form returns. Add new apparatus → confirm both flows work cleanly.
