## Architectural decisions from agent review

These bind on implementation. Items below reference them rather than re-spelling.

### A1 — Dual-writes use a SINGLE multi-path update, not two `firebaseSave` calls

**Source:** code-auditor C1+C2, devops-resilience #1.

**Problem:** Two `firebaseSave` calls = two pending-write queue entries = no atomicity. If validate rule rejects the keyed write while the array write lands, Firebase ends up in a split-brain shape. Offline replay can land them in different orders too.

**Decision:** dual-writes go through ONE Firebase `update()` call with both subpaths in a single object:
```js
ref.update({
  ['customRoles/' + idx]: arrayEntry,
  ['customRolesById/' + roleId]: keyedEntry
});
```
Firebase validates and commits atomically — if either subpath's validate fails, NEITHER lands. Applies to: [#79](https://github.com/Vergo402/paratech-struts/issues/79) (`assignedApparatus`/`assignedApparatusById`), [#112](https://github.com/Vergo402/paratech-struts/issues/112) (`customRoles`/`customRolesById`).

**Side effect:** the new keyed-write path must NOT key by array index. Key `assignedApparatusById` off `roleId` directly, not `customRoles/<idx>/assignedApparatusById/...` — otherwise it collides with #112's customRoles array→keyed migration.

### A2 — `_itemEpoch` Map needs namespaced keys

**Source:** devops-resilience #2.

**Problem:** `_itemEpoch` ([app.js:990](app.js#L990)) is keyed by raw `itemId`. v3.17.0 adds an external-equipment touched-set keyed by `opId.itemId`. If an external `itemId` collides with an inventory `itemId` (both come from `.push().key` at [app.js:4176](app.js#L4176) — same generator), `bumpEpoch(extItemId)` from the external path can drop a legitimate inventory touched entry as `epoch_advanced` at flush time.

**Decision:** namespace the epoch keys — `'inv:' + id` for inventory, `'ext:' + opId + ':' + id` for external. Affects [#107](https://github.com/Vergo402/paratech-struts/issues/107) implementation.

### A3 — External-equipment resync needs its own regex + flush function

**Source:** devops-resilience #3, code-auditor C3.

**Decision:** add `RESYNC_EXT_PATH_RE = /^\/departments\/[^/]+\/operations\/([^/]+)\/externalEquipment\/([^/]+)\/available$/` plus `markOfflineTouchedExternal(opId, itemId, localAvail)` and `flushOfflineTouchedExternal()`. Mirror the v3.16.4 inventory mark/filter/flush trio one-to-one. Document explicitly that `offlineTouchedExternalEquipment_{deptId}` is NOT subject to APP_VERSION discard (same convention as inventory touched-set survives upgrade per [app.js:1757](app.js#L1757) discussion in v3.16.4 plan).

### A4 — `_meta.roleHierarchyMigratedAt` lives at leaf, validates as number

**Source:** devops-resilience #5+#6.

**Decision:** scope `_meta.roleHierarchyMigratedAt` to a LEAF under the `departments/<deptId>` block, validate `newData.isNumber()`. Do NOT add `_meta` validate at the wrapper level (would break first-write-without-_meta, same incident shape as v3.8.2). Same scoping for `_meta.lastVerifiedAt` on externalEquipment items.

### A5 — `migrateRoleHierarchy` needs in-flight guard + field-level idempotency

**Source:** code-auditor R1+R2, devops-resilience #4.

**Decision:**
- Module-level `_roleHierarchyMigrationInFlight = new Set()` keyed by `deptId`, set on entry, cleared in `.finally`
- Field-level idempotency: `if (role.parentId !== undefined) skip` — so double-run is harmless even if `_meta` flag is lost
- Dept-switch capture: snapshot `deptId` at migration start; before each write verify `currentDeptId === capturedDeptId`, abort if not
- Write meta flag in same multi-path `update()` as parentId backfills (atomic with the migration data)

### A6 — Solo-IC mode hides multi-apparatus admin, NOT Safety / Command Staff

**Source:** battalion-chief #1 (BLOCK-level finding).

**Problem:** plan as drafted hid "roster mgmt + group structure UI" when 1 apparatus. Battalion-chief flagged: at E+0:09 when BC arrives, the first thing he does is assign Safety. If solo mode buries the Safety/Command Staff assignment, the IC fumbles at the worst moment.

**Decision:** solo-IC mode collapses these:
- Group structure UI (group picker on SP, group dropdowns)
- Multi-apparatus roster admin (apparatus checklists, apparatus dropdowns auto-resolve to the one)
- "My Role" picker (IC is the only role — auto-set)

Solo-IC mode KEEPS these visible at all times:
- IC slot (always)
- Safety Officer slot (always — mandatory per FEMA ICSSCI SM-0322 for any structural collapse incident)
- Other Command Staff slots (1 tap away — collapsed but discoverable, not hidden)

### A7 — FAB safe-area inset + z-index + hold-to-confirm

**Source:** mobile-ux #1+#2+#3, **D5 decision**.

**Decision:**
- FAB CSS: `bottom: calc(80px + env(safe-area-inset-bottom, 0)); right: 16px;` — do NOT inherit the broken `inv-quickview-btn` pattern at [style.css:982-985](style.css#L982).
- FAB z-index: explicitly < 100 (below `.modal-overlay`) so the scrim blocks taps when a modal opens. Alternative: hide via `visibility: hidden` when any modal-overlay active.
- **Accidental-tap mitigation per D5 (hold-to-confirm with countdown bar visual):**
  - Press-and-hold ~500ms required to fire the action
  - Visual feedback during hold: circular progress arc that fills around the FAB icon as the hold timer counts up
  - Release before fill complete → cancel (no action, arc resets)
  - Accessibility: also fire on Enter/Space keyboard press WITHOUT requiring hold (keyboard users get one-shot activation)
  - Eliminates accidental thumb-rest triggers entirely
  - FAB shape: icon + small label below ("Hold to start") so users know about the hold gesture (don't make the gesture invisible)

### A8 — `#startOpModal` and `#addExternalModal` need `modal-scrollbody` opt-in

**Source:** mobile-ux #4+#8.

**Decision:** [#108](https://github.com/Vergo402/paratech-struts/issues/108) (preset cards added to Start Op modal) and [#102](https://github.com/Vergo402/paratech-struts/issues/102) (full inventory-add field set in Add External Equipment modal) both push their modals past `85vh` on small phones. Both modals must opt into the v3.16.3 `.modal-scrollbody` pattern (pinned header/footer, scrollable body).

### A9 — Solo-IC promotion fires a toast on 1→2 apparatus transition

**Source:** mobile-ux #7.

**Decision:** layout changes (roster, group picker, apparatus dropdowns appearing) are easy to miss with helmet on in a smoke-filled scene. Fire a brief toast: "2nd apparatus added — full command structure now available." Doesn't block, doesn't require interaction; just directs attention.

#### P2 — [#79](https://github.com/Vergo402/paratech-struts/issues/79) — `assignedApparatus` array uses `set()` — concurrent toggles drop entries

**Symptom:** Two devices toggle apparatus assignment on the same role at the same time. Both `set('assignedApparatus', newArray)`. Last write wins; first device's toggle silently dropped.

**Root cause:** `customRoles[i].assignedApparatus` is a JS array. Granular Firebase updates aren't possible against arrays — only whole-array replacement.

**Fix:** Per **A1** — single multi-path update. New helper `setApparatusAssignment(roleId, appId, assigned)` does:
```js
ref.update({
  ['customRoles/' + idx + '/assignedApparatus']: newArray,
  ['customRolesById/' + roleId + '/assignedApparatusById/' + appId]: assigned ? true : null
});
```
Key off `roleId` (not array index) to avoid collision with [#112](https://github.com/Vergo402/paratech-struts/issues/112)'s customRoles migration. All v3.17.0 reads prefer `assignedApparatusById` (keyed), fall back to `assignedApparatus` (array).

**Files to modify:** [app.js](app.js) — every `assignedApparatus.push/filter/splice/indexOf` site (locate with `grep -n assignedApparatus app.js`). [database.rules.json](database.rules.json) — `assignedApparatusById/<appId>` validate: `newData.isBoolean()`.
