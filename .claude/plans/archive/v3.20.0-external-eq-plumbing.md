## Context

External equipment is the field-IC's escape hatch for visiting departments who arrive on scene without a FieldShore account: an IC opens **Command → External Equipment**, adds the visiting dept's stock (struts, extensions, plates), and from that moment forward that stock is supposed to be deployable on the operation's shore points just like apparatus-owned inventory.

It works on Command (where the operator added it) but not where it counts — the Deploy flow on shore points behaves as if the external stock doesn't exist, and the Quick View "Available Inventory" sidebar can't see it either. hfd217 flagged this twice (in v3.18.0 feedback and again in v3.18.1), the first triage misread it as a display-only gap, GATE 2 deferred it pending surface clarification, and the user's clarification on 2026-05-25 made the real shape clear: **the external equipment never moves into "available inventory" that can be pulled during the operation.** That's a deploy-pipeline gap, with the Quick View sidebar as the operator-visible symptom.

The fix is small and surgical — one read-site swap in `deployShorePoint()` plus merging external eq into the Quick View sidebar — but the Quick View merge is additive UI behavior, so it ships as MINOR.

**Inventory tab is explicitly NOT touched.** Per Alex's 2026-05-25 scope decision, the Inventory tab stays as dept-owned gear only. External equipment is op-scoped and ephemeral — adding it to the Inventory tab would blur the "this is mine" vs "this is borrowed" boundary and contaminate Excel import/export. The operator who wants "what's available right now during this op" uses Quick View.

#80 (concurrent-deploy phantom-double inventory allocation) was also Release-labelled v3.20.0 in the Project, but the full fix is the Cloud Function for atomic allocate+create, which is gated on the v4.0.0 per-device UID auth landing first. The v3.15.0 `makeAllocateDecrementer` mitigation already catches the v=0 race for the most common scenarios. **Defer #80 fully to v4.0.0** per Alex's 2026-05-25 decision — re-label in Project at scope-in.

## Root cause (issue #127)

`extQuickAdd()` ([app.js:4483](app.js:4483)) writes external equipment to `activeOperation.externalEquipment[itemId]` with the correct shape (`available: 1`, `quantity: 1`, typed strut / extension / plate). The write path is fine.

`getOperationInventory()` ([app.js:4790](app.js:4790)) merges external items into the deployable inventory pool when `ext.available > 0`, stamping a synthetic `apparatus: 'external-{id}'` so consumers can distinguish them.

The Deploy flow in `deployShorePoint()` ([app.js:6105](app.js:6105)) uses `opInv = getOperationInventory()` (line 6144) for strut lookup (line 6145) and plate lookup (line 6189). External-equipment struts and plates work today through this path.

**The gap is at [app.js:6157](app.js:6157)** — the extension lookup reads `localInventory.find(...)` directly, not `opInv`. That bypasses `getOperationInventory()` entirely, so an external extension is never findable for deploy. Same scope already has `opInv` in hand at line 6144 — this is a one-line read-site mismatch left over from when `getOperationInventory()` was introduced.

The Quick View **display** surface also misses external eq:
- `renderQuickViewInventory()` ([app.js:~8361](app.js:8361)) — Quick View "Available Inventory" sidebar. Reads `localInventory` only. External items invisible despite being deployable through the Command tab.

The Command tab's `renderExternalEquipmentList()` ([app.js:~5010](app.js:5010)) already shows external eq correctly — that's the surface the operator used to add it in the first place. The Inventory tab is intentionally out of scope (see Context).

## Fix design

### Fix 1 — External equipment through the full deploy/return pipeline

**Scope expanded by GATE 2 review (code-auditor + skeptical-senior-engineer, 2026-05-25):** the original "swap line 6157" was correct but insufficient. The strut path already branches on `.external` at all four sites (lookup, decrement, transaction, return); extensions don't at any of them, and **plates don't at the downstream sites either** (the plate find at `opInv` works, but decrement/compensate/transaction/return all use `localInventory.find` which returns undefined for external plates — silent loss). Plate-path asymmetry is a pre-existing prod bug surfaced by this review. v3.20.0 closes the full extension and plate symmetry in one pass.

**Pattern to mirror** — the strut path's existing branch (e.g., `runDeployTransactions` lines 7645–7654, `returnInventoryItems` lines 7705–7714) is the template. Every site that touches an inventory item's `available` count must branch on `item.external` (or `sp.deployedX.external` on the return side) and route to either:
- `activeOperation.externalEquipment[id]` + `operationsRef.../externalEquipment/{id}/available` + `bumpEpoch('ext:' + opId + ':' + id)` + `markOfflineTouchedExternal(opId, id, available)`
- `localInventory.find(i => i.id === id)` + `inventoryRef.child(id).child('available')` + `bumpEpoch(id)` + `markOfflineTouched(id, available)`

Bundling avoids two reviewer rounds and aligns with the "fix the full pipeline" framing operators expect when v3.20.0 ships.

**Concrete diff template for an inline branch** (use this pattern at every site):

```diff
- for (const ext of extInvItems) ext.available = Math.max(0, ext.available - 1);
+ for (const ext of extInvItems) {
+   if (ext.external && activeOperation.externalEquipment && activeOperation.externalEquipment[ext.id]) {
+     const e = activeOperation.externalEquipment[ext.id];
+     e.available = Math.max(0, (e.available || 0) - 1);
+   } else {
+     ext.available = Math.max(0, ext.available - 1);
+   }
+ }
```

```diff
- guards.push({ ref: inventoryRef.child(ext.id).child('available'), ... });
- bumpEpoch(ext.id);
+ const extRef = ext.external
+   ? operationsRef.child(activeOperation.id).child('externalEquipment').child(ext.id).child('available')
+   : inventoryRef.child(ext.id).child('available');
+ if (ext.external) bumpEpoch('ext:' + activeOperation.id + ':' + ext.id);
+ else bumpEpoch(ext.id);
+ guards.push({ ref: extRef, ... });
```

**Inline (not helper-extracted):** the strut path inlines these branches and they're correct. Matching the existing style outweighs DRY at this scope. A future refactor can DRY all three (strut + ext + plate) together — out of scope for v3.20.0.

### Fix 2 — Quick View sidebar display

`renderQuickViewInventory()` ([app.js:~8361](app.js:8361)): merge `activeOperation?.externalEquipment` (items with `available > 0`) into the rendered list with full source context.

**Refined per mobile-ux + battalion-chief GATE 2 review (2026-05-25):** original "single-line `ES-E [EXT] Yonkers FD / Engine 5`" was wrong — would overflow the row, push the count badge off-screen on narrow mobile, and use the runner-orange `.ext-badge` color which is the active runner-phase status color (semantic collision). Revised:

**Row structure — two visual lines using existing `.qv-name` + `.qv-app` sub-label pattern:**

```html
<div class="inv-qv-item">
  <div class="qv-left">
    <span class="qv-name">ES-E <span class="qv-ext-badge" role="img" aria-label="External equipment">EXT</span></span>
    <span class="qv-app" title="Yonkers FD / Engine 5">Yonkers FD / Engine 5</span>
  </div>
  <span class="qv-count">1</span>
</div>
```

- **`qv-name` row** (top, primary): item label + scoped `qv-ext-badge` pill. Operator scans gear type from this line under stress.
- **`qv-app` sub-label** (bottom, 11px grey): `deptName / apparatus`. Visually subordinate — already the project's pattern for secondary metadata in Quick View. Addresses battalion-chief Concern 1 (provenance must not fight gear-type scanning).
- **`title` attribute** on the sub-label: desktop hover shows full text when truncated. Escaped via `escapeAttr()` (one of the two attribute contexts in the new code).
- **A11y on badge:** `role="img" aria-label="External equipment"` — screen reader announces meaning instead of reading "EXT" literally.
- **Escape `deptName` + `apparatus`** with `escapeHtml()` in text contexts, `escapeAttr()` in the `title=""` attribute.

**Scoped CSS — DO NOT clobber existing `.ext-badge`:**

The project already has an `.ext-badge` class at [style.css:606](style.css:606) and a dark-mode override at [style.css:2212](style.css:2212), both using runner-orange (`--runner-bg` / `--runner-text` = `#FFCC80` / `#8A3300`). It's the badge used by `renderExternalEquipmentList` on the Command tab. Reusing the same class+colors for Quick View creates semantic collision with the runner-phase status color. Per mobile-ux finding #1, introduce a NEW scoped class `.qv-ext-badge` with blue tokens (the project already uses blue for `.ext-chip` extension context):

```css
/* style.css — add near the existing .ext-badge block (light mode default) */
.qv-ext-badge {
  background: #BBDEFB;
  color: #1565C0;
  border: 1px solid #1565C0;
  font-size: 11px;
  font-weight: 700;
  padding: 2px 6px;
  border-radius: 3px;
  vertical-align: middle;
  flex-shrink: 0;
  margin-left: 4px;
}

/* style.css — inside the existing :root[data-theme="dark"] block, near line 2212 */
:root[data-theme="dark"] .qv-ext-badge {
  background: #1A2A3A;
  color: #42A5F5;
  border-color: #42A5F5;
}
```

Contrast: light `#1565C0` on `#BBDEFB` = 5.4:1 (AA pass); dark `#42A5F5` on `#1A2A3A` ≈ 5.2:1 (AA pass). Matches the project's existing blue-family tokens used for extension chips (mobile-ux finding #5).

**Row truncation CSS — required to keep count badge visible at long names:**

```css
.inv-qv-item .qv-left {
  flex: 1;
  min-width: 0;
  overflow: hidden;
}
.inv-qv-item .qv-name,
.inv-qv-item .qv-app {
  display: block;
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}
```

These rules MAY already exist on `.qv-left` or `.qv-name`; verify in style.css ~lines 1114–1130 during impl. Add only what's missing. Without `min-width: 0` on the flex child, ellipsis won't fire because flex defaults to `min-width: auto` and the child refuses to shrink below content. Apparatus-owned rows have shorter content so they don't hit this today, but external rows with dept+apparatus suffixes will.

Match the tri-state pattern v3.18.1 added (gate on `activeOperation` existence, not on `assignedApparatus.length`). External-eq rows show only when there's an active op (consistent with where the data lives).

## Lessons-learned hooks (for the post-ship narrative)

- The v3.18.1 GATE 2 reasoning ("three candidate surfaces, ambiguous which one") was a real bug under-counted as a display-polish item. The fix turned out to be **one of the surfaces (deploy) plus one visibility surface (Quick View)** — the deploy surface was the load-bearing one and the v3.18.1 triage missed it because the extension lookup at app.js:6157 is structurally different from the strut+plate lookups (`localInventory.find` vs `opInv.find`). The Inventory tab gap that the v3.18.1 triage also flagged turned out to be a non-issue — Inventory tab is dept-owned-only by design, and adding external eq there would have blurred conceptual lines without solving the user's actual problem.
- For future triage: when an in-app feedback report says "X isn't registering as available," check the **deploy pipeline first** (the read site that gates allocation) before the display surfaces. Display surfaces are downstream symptoms; the deploy pipeline is the load-bearing semantic.
- Conceptual separation matters: "things I own" (Inventory tab + Excel export) and "things deployable in this op" (Quick View + Command) are different views with different lifecycles. External eq belongs to the second category only.
