# Plan: v3.5.2 — SAFETY HOTFIX (Round 2 audit)

## Context

Round 2 deep audit (`/Users/alex/Library/CloudStorage/OneDrive-Personal/Claude OS/Field Shore/.claude/audits/v3.5.1-deep-audit-round2.md`) found **3 safety-critical bugs in the strut algorithm** that Round 1 missed entirely:

- **S1:** Double-deduction in pending shore point re-validation → wrong strut/capacity recommendation
- **S2:** ACME load table linear interpolation over-reports capacity by **17% at 11 ft** vs the Paratech O&M Manual

Plus an app-bricking bug (S4) and several silent-data-loss bugs (S5–S9).

This plan is the MINIMAL fix that has to ship before any further field use. Everything else (v3.6.0 features, v4.0.0 multi-agency overhaul) waits.

**Target version:** v3.5.2 patch. Scope: surgical. Risk: low.

**Fix:** Add missing rows from Paratech O&M Manual Table 2-7 + correct 2-3 ft values:

```javascript
// Paratech O&M Manual Table 2-7 (PN 22-796198, 02 JAN 2018) — Authoritative working loads.
// 4:1 column is from manual directly. 3:1 and 2:1 derived as manual_4:1 × 4/3 and × 2 respectively
// (cross-checked against supplier-published 2:1 tables; small discrepancies at short lengths reconciled
// in favor of the manual which is the authoritative document for AcmeThread/LockStroke).
const ACME_LOAD_TABLE = [
  [24, 40000, 26667, 20000],   // 2 ft — was 21750 4:1, manual says 20000
  [36, 40000, 26667, 20000],   // 3 ft — manual constant 2-4 ft
  [48, 40000, 26667, 20000],
  [60, 33105, 22070, 16551],   // 5 ft — NEW
  [72, 28250, 18830, 14125],
  [84, 26162, 17442, 13081],   // 7 ft — NEW
  [96, 24050, 16030, 12025],
  [108, 18277, 12183, 9138],   // 9 ft — NEW

  [132, 7866, 5243, 3932],     // 11 ft — NEW — eliminates the 17% over-reporting cliff
```

**Verification:**
- At 132" (11 ft), `getLoadCapacity(132, 2)` should return exactly 3,932 (was 4,595).
- At 24" (2 ft), 4:1 capacity should be 20,000 (was 21,750).
- Linear interpolation between 120 and 132 (for, say, 126") gives a smooth curve rather than overshooting.

**Risk:** Strictly more conservative. Any load that previously "passed" at the wrong rating may now fail — that's correct behavior. Some users may see PASS → FAIL on the same setup. Add a v3.5.2 release note explaining "Load capacities corrected to match Paratech O&M Manual — some configurations that previously passed may now require additional struts."

### Fix 2 — S1: Double-deduction in pending SP re-validation

**File:** `app.js:2846-2847`

**Current code:**
```javascript
const cacheKey = `${sp.effectiveLength || sp.requiredLength}-${sp.estimatedLoad || 0}`;
```

**Fix:** Pass `sp.requiredLength` (raw opening) not `sp.effectiveLength` (already deducted):

```javascript

// Cache key includes a deductions hash so different deduction sets don't collide.

  : 'none';
const cacheKey = `${sp.requiredLength}-${sp.estimatedLoad || 0}-${dedKey}`;
const matches = strutCache[cacheKey] || (strutCache[cacheKey] =
    findStrutCombinations(sp.requiredLength, sp.estimatedLoad || 0, 2, opInv, null, sp.deductions));
```

**Verification:** Create SP with opening 100", header=3.5", footer=3.5". Trigger pending re-validation. Confirm the result matches a fresh `findForShorePoint` call on a new SP with the same opening.

### Fix 5 — S7: Firebase listener first-fire guard for empty data

**Files:** `app.js:993-999` (inventory), `app.js:1037-1039` (apparatus)

**Current code (inventory listener):**
```javascript
inventoryRef.on('value', (snap) => {
  const data = snap.val() || {};
  localInventory = Object.entries(data).map(([id, item]) => ({ id, ...item }));
  safeSetItem('fieldstruts_inventory', JSON.stringify(localInventory));
  if (document.getElementById('screenInventory').classList.contains('active')) renderInventory();
}, (err) => onListenerError('inventory', err));
```

**Fix:** If snapshot doesn't exist AND we have local data, push local data UP to Firebase instead of overwriting local:

```javascript
let inventoryFirstFire = true;
inventoryRef.on('value', (snap) => {
  if (inventoryFirstFire && !snap.exists() && localInventory.length > 0) {
    inventoryFirstFire = false;
    // Local has data but Firebase doesn't — push local up rather than wipe local
    const payload = {};
    for (const item of localInventory) {
      const { id, ...rest } = item;
      payload[id] = rest;
    }
    firebaseSave(inventoryRef, 'set', payload);
    return;
  }
  inventoryFirstFire = false;
  const data = snap.val() || {};
  localInventory = Object.entries(data).map(([id, item]) => ({ id, ...item }));
  safeSetItem('fieldstruts_inventory', JSON.stringify(localInventory));
  if (document.getElementById('screenInventory').classList.contains('active')) renderInventory();
}, (err) => onListenerError('inventory', err));
```

Apply the same pattern to `apparatusRef` (line 1037) and the customApparatusTypes listener (line 1054). Note: the operations listener (line 1001) needs a different fix since it filters by `equalTo('active')` — see S5 above for the active-op localStorage cleanup.
