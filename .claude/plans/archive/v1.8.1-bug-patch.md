## Bugs (Priority Order)

### P1: Extension rules wrong for grey and gold struts
**Issue:** #16
**Symptom:** Three problems: (1) Grey/AcmeThread struts allow too many extensions — should max 2 extensions totaling 36". (2) Gold/LongShore struts allow 2 extensions — should only accept 1. (3) No strut results past 16' even though LS 1016 goes to 198" (16.5') without extensions.
**Root Cause:** `findStrutCombinations()` at line ~1770. The combo generator builds all `[e1, e2]` pairs from `EXTENSIONS[system]` without any system-specific limits. The only filter is `extTotal > strut.extended` (line ~1783). No max-count or max-total-length rules exist per system.
**Fix:**
1. After generating combos at line ~1778, add system-specific filters inside the `for (const [e1, e2] of combos)` loop:
   - `if (strut.system === 'LongShore' && extCount > 1) continue;` — gold gets max 1 extension
   - `if ((strut.system === 'AcmeThread' || strut.system === 'LockStroke') && extTotal > 36) continue;` — grey max 36" total extension
2. For the 16' issue: test with 192" input to verify LS 1016 (collapsed:114, extended:198) appears without extensions. If it doesn't, the bug is elsewhere (maybe a UI max length cap or input parsing issue). The algorithm itself should match since 192 is between 114 and 198.
**Test:** Search 192" — should show LS 1016. Search 200" — should show LS 1016 + one 12" extension (range becomes 126"–210"). Search 250" — should NOT show LS 1016 + two extensions.

### P2: Excel export/template broken, apparatus show as DB IDs
**Issue:** #10
**Symptom:** Exported Excel shows Firebase push IDs (like `-OsABC123def`) in the Apparatus column instead of names like "Engine 169".
**Root Cause:** `exportInventory()` at line ~4238. Line ~4246: `Apparatus: item.apparatus || ''` writes the raw `item.apparatus` which is a Firebase ID. Needs to run through `getApparatusName()` (line ~2252).
**Fix:** Change line ~4246 from:
```js
Apparatus: item.apparatus || '',
```
to:
```js
Apparatus: item.apparatus ? getApparatusName(item.apparatus) : '',
```
Also check `handleImport()` (line ~4314) — on import, it needs to reverse-map apparatus names back to IDs, or store by name. Check if the current import logic matches on apparatus name or ID.
**Test:** Export inventory, open Excel, verify apparatus column shows "Engine 169" not Firebase IDs. Re-import the exported file and verify it works.

### P2: Cannot open layout cards under Command tab
**Issue:** #11
**Symptom:** Layout section in Command view shows hierarchy groups (Building, Division, etc.) but clicking them does nothing.
**Root Cause:** `renderCommandView()` line ~3772. The layout cards are plain `<div>` elements with no `onclick` handler. Compare with Operations drill-down which uses click handlers to navigate into hierarchy levels.
**Fix:** Add `onclick` to each layout card that switches to the Operations tab and navigates the drill-down to that hierarchy level. Something like:
```js
onclick="switchTab('ops'); navigateDrillDown('${topLevel}', '${name}')"
```
Need to check if `navigateDrillDown` exists or if we need to set the drill-down state variables and call `renderOperationsView()`. The Operations view uses a breadcrumb-based drill-down — we need to set the current navigation path to match the clicked group.
**Test:** Click a Building card in Command view → should switch to Operations and show that building's shore points.

### P2: Apparatus roles not populated on role list
**Issue:** #12
**Symptom:** After assigning a role to an apparatus, the role doesn't appear immediately in the list.
**Root Cause:** `selectRole()` at line ~2667 does call `renderOperations()` at line ~2694 after closing the modal. However, `renderOperations()` renders the main operations view which includes apparatus chips with role badges (line ~2929). The issue may be that if the user is on the Command view (not Operations), `renderOperations()` doesn't update the Command view. `renderCommandView()` would need to be called separately, and it has its own Apparatus Roles section at line ~3778.
**Fix:** After `selectRole()` and `clearRole()`, also trigger a re-render of whichever view is active:
```js
closeModal('roleModal');
renderOperations();
// Also re-render command view if it's the active tab
const view = document.querySelector('.view-tab.active');
if (view && view.textContent.trim() === 'Command') renderCommandView();
```
Or simpler: call both `renderOperations()` and `renderCommandView()` — the inactive one just renders to a hidden container, no harm done.
**Test:** Open Command tab → click an apparatus → assign a role → verify the role badge appears immediately.

### P2: External equipment shouldn't require both dept and apparatus
**Issue:** #13
**Symptom:** Adding external equipment requires filling in the Department field (validated at line ~2799: `if (!deptName) { alert('Please enter a department name.'); return; }`). Apparatus defaults to "Unknown" if empty (line ~2807). User wants either dept OR apparatus to be sufficient.
**Root Cause:** `confirmAddExternal()` at line ~2791. Hard validation on `deptName` but not on `apparatus`.
**Fix:** Change validation to require at least one of the two:
```js
if (!deptName && !apparatus) { alert('Please enter a department name or apparatus.'); return; }
```
Keep the defaults: if `deptName` is empty, use apparatus as the label. If `apparatus` is empty, use `deptName`. Update `item.deptName` to default gracefully:
```js
deptName: deptName || apparatus,
apparatus: apparatus || deptName,
```
**Test:** Add external equipment with only dept name → works. Add with only apparatus → works. Add with neither → shows error.

### P2: Actual cut measurement needed before cut done
**Issue:** #17
**Symptom:** The Cut Table two-phase flow shows "Mark Cut Complete" first (no measurement input), then after marking done, shows the actual measurement input + "Send to Runner". Users want to enter the actual cut measurement BEFORE marking complete.
**Root Cause:** `renderCutTableCard()` at line ~3870. The `actionBtn` for `mode === 'active'` is just the "Mark Cut Complete" button (line ~3887). The actual measurement input only appears in `mode === 'done'` (line ~3889).
**Fix:** Add the actual measurement input alongside the "Mark Cut Complete" button in the active mode:
```js
const actionBtn = mode === 'active'
  ? `<div style="display:flex;gap:6px">
      <input type="number" inputmode="decimal" placeholder="Actual cut (optional)" id="actual-${sp.id}" style="flex:1;padding:8px;border:1px solid #E0E0E0;border-radius:6px;font-size:13px">
      <button class="btn btn-sm" style="flex:1;background:#FFF8E1;color:#F57F17;border:1px solid #F9A825;font-weight:700;min-height:44px;font-size:15px" onclick="markCutDone('${sp.id}')">✓ Complete</button>
    </div>`
  : `<button ...>→ Runner</button>`;
```
Then update `markCutDone()` to capture the actual measurement from the input field (same pattern as `sendToRunner()` at line ~3927).
Also simplify the done state — once cut is complete WITH the measurement already entered, the "Send to Runner" button can be a simple single button since the measurement was already captured.
**Test:** Go to Cut Table → enter actual measurement in the input → click Mark Complete → verify measurement is saved. Then click Send to Runner.
