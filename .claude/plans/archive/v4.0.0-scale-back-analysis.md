# v4.0.0 — Scale-Back Analysis

> **Date:** 2026-05-17
> **Context:** Alex flagged that the [v4.0.0 plan](v4.0.0-plan.md) is too aggressive — "scale back our rapid expansion." This document explores how.
> **Status:** For Alex to mull. No decisions forced.

---

## The diagnosis — where the bloat lives

The original v4.0.0 plan tries to ship in one release:
- **Per-actor identity + multi-tenancy** (Phase 3A + 3B) — large, must-do, schema-level
- **Full NIMS doctrine overhaul** (Phase 3C with 11 sub-phases including 4 NEW) — large
- **All ICS forms bundle + 3 NEW form surfaces** (Phase 3D) — medium-large
- **Strut algorithm polish + CI smoke deck** (Phase 3E) — small-medium
- **6 NEW hardening sub-phases** (Phase 3F — WCAG, reactive counts, bulk deploy, virtualization, FABs) — medium

That's roughly **30 distinct deliverables** in one 8-week window (alpha+GA). Even at 1.5 deliverables/week — which assumes near-perfect parallel work and zero rework — that's 20 weeks of nominal work compressed into 8.

The audit team's 19-reviewer consensus revised the v4.0.0 estimate from 6-8 to 8-10 weeks **before the sim findings landed**. The sim added another ~20 items. The plan's 4-week alpha + 4-week GA is unrealistic by ~50%.

There's also a quieter problem: **rapid expansion makes the agent team less effective**, not more. With 30 deliverables in flight, no single agent has stable ownership. Reviews happen on a moving target. The verification standard (every flow driven through preview) becomes uncheckable at this pace.

---

## Four options on the table

### Option A — Minimum-viable v4.0.0 (foundation + criticals only)

Ship only what's structurally required: Auth, multi-tenancy, the bare NIMS doctrine the foundation depends on, and the most safety-critical NEW items.

**Includes:**
- Phase 3A — per-actor identity, write attribution, per-agency scope (IP-001/002/004)
- Phase 3B — agency badges, IC[] collection (IP-003/013)
- Phase 3C core only — ICS_ROLES_DEFAULT expansion, preset selector, role history, `group` → `assignedResource` rename (IP-005/006/014/017/022)
- **Demob lifecycle** (IP-008) — IST-blocking, can't defer
- **Cribbing audit** (IP-009) — safety-critical, can't defer
- **Safety state surface** (IP-032) — doctrinal stop-the-line, can't defer

**Defers to v4.1.0:** All other Phase 3C work (span warnings, snapshot diff, victim locator, multi-role, render hardening), all Phase 3D NEW forms (ICS-205/208/209/SitStat), Phase 3E enhancements, all Phase 3F NEW sub-phases (WCAG, FABs, bulk deploy, virtualization).

**Timeline:** ~8 weeks (matches audit team consensus)
**Risk:** Some high-severity findings sit for 3+ months
**Defensibility:** High — "we shipped the foundation + the things you can die from"

---

### Option B — Phased v4.x train (RECOMMENDED)

Split v4.0.0 into a sequence of smaller MAJOR/MINOR releases. Each release is bounded, testable, and gives a TTX a chance to catch new issues before the next one ships.

**v4.0.0 — Foundation (~6 weeks)**
- Phase 3A + 3B fully
- Phase 3C bare minimum: ICS_ROLES_DEFAULT expansion, preset selector, role history, `group` rename
- Schema migration cutover

**v4.1.0 — Field doctrine (~6 weeks, starts ~2 weeks after v4.0.0)**
- Demob lifecycle
- Cribbing audit
- Safety state surface
- Hazards register
- SitStat view
- ICS forms expansion (202/207/209)

**v4.2.0 — UX hardening (~4 weeks)**
- ICS-205 Comms Plan
- Victim locator
- Multi-role per individual
- Span warnings + Convert to Branches
- Bulk deploy mode
- Virtualization + reactive counts + WCAG + FABs

**Total wall-clock:** ~16 weeks for v4.0.0 → v4.2.0, but **v4.0.0 ships in 6 weeks** and is field-usable. Department gets each cluster of value sooner.

**Risk:** Three migrations instead of one (each MAJOR is its own migration window). `migration-specialist` becomes the bottleneck.
**Defensibility:** Highest — each release is a coherent story; each TTX validates the previous before the next ships.

---

### Option C — Original plan (one big v4.0.0)

What's currently in `v4.0.0-plan.md`. ~13-15 weeks. Ship everything at once. Highest individual-release impact, highest risk.

**Risk:** Schedule slip is near-certain. Once it slips, where does it land? Beta TTX is the only catch, and beta is at week 10 of 13.
**Defensibility:** Low — "we tried to do everything and it took longer than promised."

---

### Option D — Feature-flag v4.0.0

Ship all the code but gate most features behind opt-in flags. Alex's dept turns them on incrementally. Defers behavioral risk without deferring code work.

**Timeline:** ~10 weeks
**Risk:** Dual-code-path maintenance cost. Every flag adds permutations to test. Every domain agent now reviews "feature on AND feature off."
**Defensibility:** Medium — "we shipped, but with safeties."

## Where each agent stands

### `architect` (me)
**Vote: Option B (phased).** The original plan was structurally one release because the v4.0-to-v5.0 roadmap framed it that way, but the sim findings have changed the math. A phased train preserves agent-team ownership (each release has a coherent owner-set), keeps verification possible at each step, and gives TTX-3/4/5 something to learn from between releases. The bottleneck risk on `migration-specialist` is real but manageable — three smaller migrations are not three times harder than one big one.

### `migration-specialist` (synthetic view)
**Vote: Option B over A.** Three migrations is more work than one. BUT each smaller migration has a tighter blast radius and a cleaner rollback. The Phase 3A identity migration alone is the highest-risk piece in the entire plan — isolating it in v4.0.0 means we can stabilize it before piling demob + cribbing + hazards on top. **Strong preference for splitting Phase 3A into its own release.**

### `nims-compliance` (synthetic view)
**Vote: A or B both acceptable.** The doctrine work is what it is — Type I preset enumeration doesn't get faster by scope-cutting. What matters is that the doctrine doesn't fragment across releases. Option B is fine **if** the v4.0.0 Phase 3C subset is a coherent doctrine commitment (e.g., "we ship Type I/II preset including all Command Staff but defer Branch tier") and not a random slice. Option A is fine because it's the smallest possible coherent doctrine commit.

### `battalion-chief` (synthetic view)
**Vote: B with reordering.** Field IC perspective: the most urgent gaps are **role history loss** (IP-006, 11+ confirmed losses), **safety state** (IP-032, stop-the-line is doctrinal), and **demob** (IP-008). Cribbing (IP-009) is critical at long incidents but not Day 1. Argue for: v4.0.0 ships role history + safety state; v4.1.0 ships demob + cribbing. Not what Option B says, but worth considering.

### `usar-task-force-leader` (synthetic view)
**Vote: B but only if v4.0.0 ships multi-tenancy fully.** TFL cares about cache integration on arrival — partial multi-tenancy means TF-State Cache gets overwritten by local-FD writes. Phase 3A + 3B fully done is the floor. Cribbing + demob + SitStat are valuable but TFL can keep working without them; per-agency write scope, no.

### `release-manager` (synthetic view)
**Vote: B, but consolidate v4.2.0 work into v4.1.0 if you can.** Three migrations means three full release ceremonies — version bumps, manual updates, GitHub releases, schema cutover testing. Each costs roughly half a developer-week of overhead. If v4.1.0 and v4.2.0 can merge into one ~8-week release, save the overhead.

### `code-auditor` (synthetic view)
**Vote: A or B.** Either is auditable. **Strong vote against C and D.** Option C compresses audit time past usefulness. Option D's feature-flag matrix makes audit surface combinatorial.

### `scenario-conductor` (synthetic view)
**Vote: B for the multi-TTX opportunity.** Each release in Option B gets its own pre-ship TTX run. That's how the sim infrastructure pays off. Option A ships once and tests once. Option C tests under time pressure.

## Honest recommendation

**Option B (phased) with one modification:** consider B's v4.1.0 + v4.2.0 merger into a single v4.1.0 release per `release-manager`'s point. That gives you:

- **v4.0.0 in ~6 weeks:** Auth + multi-tenancy + minimal NIMS. Schema migration done. **Foundation that everything else builds on.**
- **v4.1.0 in ~10 weeks:** Demob + cribbing + safety + hazards + SitStat + ICS forms + UX hardening. Field doctrine completion.
- **Total:** ~16 weeks to feature-complete v4.1.0, but v4.0.0 is field-usable in 6 weeks.

This is the answer that respects "scale back rapid expansion" without skimping on what the sim flagged as critical. v4.0.0 ships fast and bounded; v4.1.0 carries the doctrine cargo when the foundation is stable.

The trade-off: `migration-specialist` is on the hook for two MAJOR migrations within 16 weeks instead of one. That's real but doable.

Under Option C (original), every agent is in every release the whole time. Under B, agents rotate on/off and stay sharp.
