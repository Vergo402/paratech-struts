## Bugs for this release

### Bug 1: Default Quick Find should have no strut type pre-selected
**Issue:** #38
**Symptom:** Quick Find has all 3 system toggles (Gold, Grey, Lockstroke) active by default. Users should select which types they have, not start with all selected.
**Root Cause:** `index.html` lines 141-147 — all three `<button class="system-toggle active ...">` have the `active` class by default.
**Fix:** Remove the `active` class from all three toggle buttons in `index.html`:
```html
<button class="system-toggle gold" id="toggleGold" ...>
<button class="system-toggle grey" id="toggleGrey" ...>
<button class="system-toggle lockstroke" id="toggleLockstroke" ...>
```
Then verify `getActiveSystemFilter()` (app.js line 262) returns an empty array when no toggles are active, and confirm `findStrutCombinations()` (line 121) shows ALL struts when `systemFilter` is empty (line 141-142 already handles this — empty array means no filtering).

### Bug 2: Base plate card shows wrong dimensions — needs height for deductions
**Issue:** #39
**Symptom:** Plate names include physical size (e.g., "Rigid Base 6"") which users confuse with the deduction height. The `+height` used for effective length calculation needs to be the primary displayed dimension.
**Root Cause:** `BASE_PLATES` (app.js line 52) — plate names embed the physical size (6", 12", 3"x4"). The plate picker (line 3566-3571) and Quick Add (line 973) show both name and height but the name's embedded size dominates visually.
**Fix:** Make the `+height"` the primary dimension on all plate displays:
1. **Quick Add plates** (line 973): Change `<span class="plate-ht">${plate.height}"</span>` to more prominent display like `<span class="plate-ht">+${plate.height}" ht</span>` with bold styling.
2. **Plate picker** (line 3571): Already shows `+${plate.height}"` — make it bolder/larger and de-emphasize the name's embedded dimensions.
3. **Deduction summary** in result cards (line 340-341): Already shows plate name — ensure the height deduction is clearly visible.
Consider updating plate names to remove embedded dimensions, or make the height stand out more visually.

### Bug 3: "Multi-Base" should be renamed to "Multi-Tip"
**Issue:** #40
**Symptom:** The connector plate named "Multi-Base" is incorrect — the correct Paratech terminology is "Multi-Tip".
**Root Cause:** `BASE_PLATES` array line 58: `name:'Multi-Base'`
**Fix:** Change `name:'Multi-Base'` → `name:'Multi-Tip'` in the BASE_PLATES constant.

## Features for this release

### Feature 1: Collapsible operation sections
**Issue:** #41
**Scope:** Small (~30 min)
**Description:** Operations view sections (status lanes, hierarchy groups) should be collapsible so users can focus on the section they're working with.
**Implementation:** The lane collapse pattern already exists — `toggleLane()` at app.js line 2242 and `laneCollapsedState` object. Extend this pattern to the main operation sections (assigned apparatus list, shore point lanes, etc.) by wrapping section headers in clickable divs that toggle visibility of their content.

### Feature 2: Apparatus type hierarchy
**Issue:** #42
**Scope:** Medium (~1 hour)
**Description:** Assigned apparatus should be categorized by type: Chief, Engine, Ladder, Rescue, Squad, Task-Force. Currently apparatus are flat list items.
**Implementation:**
1. Add an `apparatusType` field to apparatus creation/editing (options: Chief, Engine, Ladder, Rescue, Squad, Task-Force, Other).
2. In `renderAssignedApparatus()` (line 1102), group apparatus by type before rendering.
3. Display type headers (sorted in the hierarchy order above) with apparatus listed under each.
4. Store `apparatusType` in Firebase apparatus data.

### Feature 3: Manually assign apparatus on operation page
**Issue:** #43
**Scope:** Small (~30 min)
**Description:** Users want to assign apparatus directly from the operation page, not just during op creation.
**Implementation:** The current flow only assigns during `startOperation()` (line 2015). Add an "Assign Apparatus" button on the operations view that opens a picker of unassigned apparatus. Use `toggleApparatus()` (line 1115) logic to add/remove from `activeOperation.assignedApparatus`. Render the button near the assigned apparatus list.

### Feature 4: Combine apparatus into task force/group
**Issue:** #44
**Scope:** Medium (~1-2 hours)
**Description:** During an operation, combine multiple apparatus into a named group (task force, strike team, etc.).
**Implementation:**
1. Add `apparatusGroups` to operation data: `{ groupId: { name: 'TF-1', type: 'Task Force', members: ['app1', 'app2'] } }`
2. Add "Create Group" button on operations view that opens a modal to name the group, select type, and pick member apparatus.
3. Render grouped apparatus together in the assigned list with the group name as header.
4. Groups are purely organizational — individual apparatus keep their inventory.
**Dependencies:** Ties into #42 (apparatus types) and #45 (NIMS/ICS terminology).

### Feature 5: Review and apply NIMS/ICS terminology
**Issue:** #45
**Scope:** Medium (~1 hour)
**Description:** Review all labels and terminology in the app against NIMS/ICS standards and update where needed. Terms like "group", "division", "task force" should match ICS definitions.
**Implementation:** Audit pass on all UI labels and field names:
- Verify hierarchy levels (Building → Division → Floor → Team) match ICS terminology
- Check ICS_ROLES names and abbreviations against NIMS standards
- Verify group/division/task force usage in apparatus grouping
- Update shore point form field labels as needed
This is primarily a label/text change with no structural code changes.

### Feature 6: Drag-and-drop ICS org chart node repositioning
**Issue:** #46
**Scope:** Large (~4+ hours)
**Description:** The ICS org chart nodes need to be draggable to restructure the hierarchy in real time. Currently nodes are tappable (v2.2.0) but fixed in position.
**Implementation:** This is a significant feature requiring:
1. Touch drag event handling on `.org-node` elements
2. Drop zone detection for valid parent/child relationships
3. Real-time re-rendering of the chart during drag
4. Firebase sync of new hierarchy positions
5. Constraint logic — IC stays at top, certain roles can only parent certain children
**Recommendation:** Defer to v3.0.0. The current tap-to-assign (v2.2.0) handles the core need. Drag-and-drop on mobile touch devices is complex and may require a library like SortableJS.
