# Plan: v3.8.0 — Inventory display + individual cut tracking

## Context
2 new feedback items from Firebase (v3.7.5, dept hfd217): 1 bug (inventory display not updating after deployment) and 1 feature (wood cuts should track per-card, not per-group).

---

## Feedback Triage

### Bugs for this release

**#64 — Available inventory not updating when shore points are created**

The in-memory inventory IS correctly decremented during deployment (`deployShorePoint()` at app.js:3662-3672 modifies `localInventory` objects directly). But `renderInventory()` is never called after deployment — only `renderOperations()` is (app.js:3710). So the Inventory tab doesn't reflect the new "deployed" counts until the user switches away and back (tab switch triggers `renderInventory()` at line 368).

Additionally, if the user opens the shore point form a second time to deploy more, the recommendation results are generated from `findStrutCombinations()` which reads `localInventory` — this IS correctly updated in memory. So the core data is right, but the display lags.

### Features for this release

**#65 — Individual wood cut tracking per shore point**

Currently, `markCutDone()` (app.js:4415) and `sendToRunner()` (app.js:4389) both call `getGroupMembers(spId)` and apply the status change to ALL members of the group. This means if you mark one shore point's wood as cut, all grouped points are also marked cut.

The user's feedback: wood cuts may be delayed on some points. You need to track which individual cards have their wood cut and which don't, even within a group.

## Implementation

### Bug: Inventory display not updating (#64)
**Issue:** [#64](https://github.com/Vergo402/paratech-struts/issues/64)
**Symptom:** Inventory tab still shows old available/deployed counts after creating shore points
**Investigate:** `deployShorePoint()` at app.js:3696-3711 — the post-deploy block calls `persistInventory()` and `renderOperations()` but not `renderInventory()`
**Fix:** Add `renderInventory()` call after `persistInventory()` at line 3709. This is safe even if the inventory tab isn't active — `renderInventory()` writes to the `#screenInventory` container which is hidden when another tab is active. Also add `renderInventory()` after `returnEquipment()` (app.js ~4580-4610 area) for the same reason — returned items should update the display immediately.

### Feature: Individual wood cut tracking (#65)
**Issue:** [#65](https://github.com/Vergo402/paratech-struts/issues/65)
**Symptom:** Marking one grouped shore point's wood as cut marks ALL group members' wood as cut
**Investigate:**
- `markCutDone()` at app.js:4415 — loops over `getGroupMembers(spId)` and sets `cutMarkedDone: true` on every member
- `sendToRunner()` at app.js:4389 — loops over `getGroupMembers(spId)` and sets `status: 'runner'` + `cutMarkedDone: false` on every member

**Fix:** Wood cutting operations should act on the INDIVIDUAL shore point, not the group. The group behavior makes sense for status transitions (deployed → cutting → runner → placed) because the physical shore system moves together, but the wood cut tracking is per-card because each piece of lumber is cut separately.

Changes to `markCutDone()`:
- Remove the `getGroupMembers()` call — operate only on the single shore point identified by `spId`
- Find the single point: `const sp = activeOperation.shorePoints.find(p => p.id === spId)`
- Apply `cutMarkedDone: true` (and optional `actualCutLength`) to just that point

Changes to `sendToRunner()`:
- Keep the group behavior for the `status: 'runner'` transition (the physical system moves together)
- But do NOT reset `cutMarkedDone` on members that haven't been individually marked yet — only reset it on members where it was already true
- OR: leave `cutMarkedDone` alone entirely during the runner transition (it's reset when they're individually cut again)

Changes to cut table rendering (app.js ~4280-4360):
- The "Needs Cutting" filter (line 4282) already checks `!sp.cutMarkedDone` per-point, so individual tracking will work without rendering changes
- The "Cuts Done" filter (line 4293) already checks `sp.cutMarkedDone` per-point — also fine

**Key insight:** The rendering already supports individual tracking. Only the mutation functions need to change.
