# FieldStruts v4.0 → v5.0 — PWA to Native Platform Roadmap

## Context

FieldStruts is at v3.7.1 — a vanilla HTML/CSS/JS PWA that works well for strut finding and cut tracking but is overloaded for mobile field use at scale. The current HTML interface doesn't work for long-term growth: the operations tab is crowded, shore points overwhelm at 5+, the command page is unusable on phones, and settings is disorganized.

Alex's plan: evolve FieldStruts into native iOS + Android apps (phones) with a desktop/tablet command module. Start free with his department, grow via partner depts and r/firefighting, then pursue freemium licensing or sale to Paratech/AirShore. Budget is minimal ($0-500 initially), timeline is 6-12 months, and Alex + Claude are the dev team.

This plan supersedes the v4.0.0 section of MASTER-PLAN.md with a broader strategic roadmap.

---

## Framework Decision: React Native (Expo) + React (web)

**Why Expo/React Native over Flutter, Capacitor, or enhanced PWA:**

1. **Claude is the developer.** Claude's training data has vastly more React/RN code than Flutter/Dart — this means faster, more correct code generation. This is the single biggest productivity factor.
2. **Expo eliminates the build trap.** Alex never debugs Xcode signing or Gradle configs. `eas build` produces signed binaries in the cloud.
3. **TypeScript shared core.** The strut algorithm, data constants, and Firebase layer live in a shared package used by both mobile and web. Not possible with Flutter (Dart).
4. **`@react-native-firebase`** gives native offline persistence for free — replacing the entire 100+ line `pendingWrites` queue system.

**Desktop/tablet command module:** React web app (Vite + React), NOT Electron. Hosted on Firebase Hosting or Vercel. A web app is simpler, always up-to-date, and doesn't require another build target.

## Architecture: Turborepo Monorepo

```
fieldstruts/                    # NEW private repo
├── packages/
│   ├── core/                   # Shared TypeScript — pure logic, no UI
│   │   └── src/
│   │       ├── struts/         # STRUTS[], load tables, findStrutCombinations()
│   │       ├── operations/     # Shore point lifecycle, deductions, cut length
│   │       ├── ics/            # ICS roles, reparenting, NIMS presets
│   │       ├── inventory/      # Deploy/return transactions, types
│   │       ├── firebase/       # Schema helpers, sync, auth
│   │       └── vendor/         # Vendor-agnostic strut data model
│   ├── mobile/                 # React Native (Expo) — phone-optimized
│   │   └── app/(tabs)/         # Quick Find | Operations | Inventory | Settings
│   └── web/                    # React web — tablet/desktop command module
│       └── src/pages/          # Dashboard | Command | Operations | Admin | Reporting
├── pwa/                        # Current PWA — stays live as free/demo
│   ├── index.html, app.js, style.css, sw.js
└── turbo.json
```

**What is shared (core):** Strut finder algorithm, all data constants, shore point lifecycle, deduction math, Firebase schema, offline sync logic, vendor data model. ~30-40% of code by lines, ~80% of business logic.

**What is NOT shared:** All UI components, navigation, storage adapters, camera/GPS/QR (mobile only), drag-and-drop org chart (web only).

## Backend: Stay on Firebase

Firebase is correct. Key reasons:
- React Native Firebase gives offline persistence with one config flag (replaces the entire manual `pendingWrites`/`localStorage` system)
- Firebase Cloud Messaging handles push notifications
- Firebase Storage handles photo uploads (replacing the base64-in-RTDB hack)
- Cost at pilot scale: $0-5/month (Spark free plan → Blaze pay-as-you-go)

**Schema evolution** (new schema for native app, PWA keeps old):

```
# Current (v3.7.1): /departments/{deptId}/operations/{opId}/...
# Target (v5.0.0):

/agencies/{agencyId}/
  name, inventory, apparatus, settings, members/{uid}

/operations/{opId}/             # Top-level, not nested under dept
  agencies: { agencyId: { joinedAt } }
  shorePoints/{spId}/...
  roles, customRoles, photos, activity
  joinCode: string              # QR code incident join

/incidents/{joinCode}/          # QR-to-operation lookup
  operationId, createdBy
```

## Vendor-Agnostic Data Model

```typescript

interface VendorStrutModel {
  id: string;
  vendor: string;          // 'paratech' | 'airshore' | 'speed-shore' | ...
  model: string;
  system: string;
  color: string;
  collapsedLength: number; // inches
  extendedLength: number;  // inches
  compatibleExtensions: number[];
  extensionRules: { maxCount: number; maxTotalLength: number; };
}

interface VendorDataPack {
  vendor: string;
  displayName: string;
  struts: VendorStrutModel[];
  loadTables: VendorLoadTable[];
  extensions: Record<string, number[]>;
  connectorPlates: ConnectorPlate[];
}
```

Ships with Paratech as default. Architecture supports adding any vendor's data without code changes.

## What NOT to Do

1. **Don't eject from Expo.** You lose the managed build system.
2. **Don't switch to Firestore.** RTDB is simpler, cheaper, and already working.
3. **Don't build Electron for desktop.** Web app on Firebase Hosting is simpler and always up-to-date.
4. **Don't implement your own offline sync.** React Native Firebase's built-in persistence replaces all of it.
5. **Don't share UI components between mobile and web.** Share business logic only.
6. **Don't contact manufacturers before having paying customers.**

### Scope Boundaries — What FieldStruts IS and IS NOT

**Consensus from IST Plans Chief (#13), Logistics Chief (#14), and multiple reviewers:**

FieldStruts is a **shoring operations module** that exports data into the broader ICS ecosystem. It is NOT a replacement for ICS planning tools (D4H, Veoci, WebEOC).

**IN SCOPE — Build and invest:**
Strut finder, shore point lifecycle, cut table, equipment inventory (struts + lumber + plates), apparatus tracking, ICS org chart (internal TF use), operational period snapshots, photos, GPS, QR join, training mode

**IN SCOPE — Build as data export only:**
ICS-203 (auto-populated), ICS-211 (from check-in), ICS-201 (partial), ICS-204 (if division assignments exist), CSV/JSON for all data types

**OUT OF SCOPE — Do not build:**
ICS-202, ICS-205, ICS-206, full planning cycle workflow, general ICS resource management, food/medical vitals/heavy equipment/rigging
