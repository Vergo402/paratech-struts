# FieldShore v4.0 → v5.0 — PWA to Native Platform Roadmap

## Context

FieldShore is at v3.11.1 — a vanilla HTML/CSS/JS PWA that works well for strut finding and cut tracking but is overloaded for mobile field use at scale. The current HTML interface doesn't work for long-term growth: the operations tab is crowded, shore points overwhelm at 5+, the command page is unusable on phones, and settings is disorganized.

Alex's plan: evolve FieldShore into native iOS + Android apps (phones) with a desktop/tablet command module. Start free with his department, grow via partner depts and r/firefighting, then pursue freemium licensing or sale to Paratech/AirShore. Budget is minimal ($0-500 initially), timeline is 6-12 months, and Alex + Claude are the dev team.

This plan supersedes the v4.0.0 section of MASTER-PLAN.md with a broader strategic roadmap.

**Strategic pivot — 2026-05-17: Local-first scope for v4.0 (Phase 0).** The original Phase 0 was scoped against the Surfside TTX-2 federal/USAR Type I simulation. That scope outgrew the actual user base. v4.0 is being reframed around the everyday municipal fire department persona — Type IV/V incidents (car into building, residential partial collapse, light commercial collapse), 1 dept, 1 IC, 2-4 apparatus, 5-20 shore points. Federal/USAR scope is **deferred to a Federal Future release** (likely v5.x or v6.x) once 10+ local departments have validated the product. The broader strategy (monorepo, shared core, React Native mobile, web command module, App Store launch, freemium → dept license → manufacturer engagement) — Phases 1 through 4 — is unchanged.

---

## Framework Decision: React Native (Expo) + React (web)

**Why Expo/React Native over Flutter, Capacitor, or enhanced PWA:**

1. **Claude is the developer.** Claude's training data has vastly more React/RN code than Flutter/Dart — this means faster, more correct code generation. This is the single biggest productivity factor.
2. **Expo eliminates the build trap.** Alex never debugs Xcode signing or Gradle configs. `eas build` produces signed binaries in the cloud.
3. **TypeScript shared core.** The strut algorithm, data constants, and Firebase layer live in a shared package used by both mobile and web. Not possible with Flutter (Dart).
4. **`@react-native-firebase`** gives native offline persistence for free — replacing the entire 100+ line `pendingWrites` queue system.

**Desktop/tablet command module:** React web app (Vite + React), NOT Electron. Hosted on Firebase Hosting or Vercel. A web app is simpler, always up-to-date, and doesn't require another build target.

## Architecture: Turborepo Monorepo

```
fieldshore/                     # NEW private repo
├── packages/
│   ├── core/                   # Shared TypeScript — pure logic, no UI
│   │   └── src/
│   │       ├── struts/         # STRUTS[], load tables, findStrutCombinations()
│   │       ├── operations/     # Shore point lifecycle, deductions, cut length
│   │       ├── ics/            # ICS roles, reparenting, NIMS presets
│   │       ├── inventory/      # Deploy/return transactions, types
│   │       ├── firebase/       # Schema helpers, sync, auth
│   │       └── vendor/         # Vendor-agnostic strut data model
│   ├── mobile/                 # React Native (Expo) — phone-optimized
│   │   └── app/(tabs)/         # Quick Find | Operations | Inventory | Settings
│   └── web/                    # React web — tablet/desktop command module
│       └── src/pages/          # Dashboard | Command | Operations | Admin | Reporting
├── pwa/                        # Current PWA — stays live as free/demo
│   ├── index.html, app.js, style.css, sw.js
└── turbo.json
```

**What is shared (core):** Strut finder algorithm, all data constants, shore point lifecycle, deduction math, Firebase schema, offline sync logic, vendor data model. ~30-40% of code by lines, ~80% of business logic.

**What is NOT shared:** All UI components, navigation, storage adapters, camera/GPS/QR (mobile only), drag-and-drop org chart (web only).

## Backend: Stay on Firebase

Firebase is correct. Key reasons:
- React Native Firebase gives offline persistence with one config flag (replaces the entire manual `pendingWrites`/`localStorage` system)
- Firebase Cloud Messaging handles push notifications
- Firebase Storage handles photo uploads (replacing the base64-in-RTDB hack)
- Cost at pilot scale: $0-5/month (Spark free plan → Blaze pay-as-you-go)

**Schema evolution** (new schema for native app, PWA keeps old):

```
# Current (v3.11.1): /departments/{deptId}/operations/{opId}/...
# Target (v5.0.0):

/agencies/{agencyId}/
  name, inventory, apparatus, settings, members/{uid}

/operations/{opId}/             # Top-level, not nested under dept
  agencies: { agencyId: { joinedAt } }
  shorePoints/{spId}/...
  roles, customRoles, photos, activity
  joinCode: string              # QR code incident join

/incidents/{joinCode}/          # QR-to-operation lookup
  operationId, createdBy
```

## Vendor-Agnostic Data Model

```typescript

interface VendorStrutModel {
  id: string;
  vendor: string;          // 'paratech' | 'airshore' | 'speed-shore' | ...

  system: string;
  color: string;
  collapsedLength: number; // inches
  extendedLength: number;  // inches
  compatibleExtensions: number[];

interface VendorDataPack {
  vendor: string;
  displayName: string;
  struts: VendorStrutModel[];
  loadTables: VendorLoadTable[];
  extensions: Record<string, number[]>;
  connectorPlates: ConnectorPlate[];
}
```

## What NOT to Do

1. **Don't eject from Expo.** You lose the managed build system.
2. **Don't switch to Firestore.** RTDB is simpler, cheaper, and already working.
3. **Don't build Electron for desktop.** Web app on Firebase Hosting is simpler and always up-to-date.
4. **Don't implement your own offline sync.** React Native Firebase's built-in persistence replaces all of it.
5. **Don't share UI components between mobile and web.** Share business logic only.
6. **Don't contact manufacturers before having paying customers.**

## Federal Future — what's deferred from v4.0

On 2026-05-17 Alex made a strategic call to reframe v4.0 (Phase 0) around the everyday municipal fire department persona — Type IV/V incidents, single dept, 1 IC, 2-4 apparatus, 5-20 shore points. The items below were originally in v4.0 scope (driven by Surfside TTX-2 simulation findings) and are now deferred. They re-enter the plan in v5.x or later, gated on **10+ local departments using FieldShore in real Type IV/V incidents**.

**Why deferral, not deletion:** the federal-scale work isn't wrong — it's just out of sequence. Local product-market fit is the cheaper, faster validation gate. Federal scope without local validation is a path to a brittle product nobody uses.

**Deferred catalog (canonical source: `.claude/plans/v4.0.0-plan.md`):**

- **Multi-agency auth + agency badges + per-agency write scope** — single-dept UID auth lands in v4.0; multi-agency is its own design problem (membership graph, cross-agency read visibility, dispatch attribution)
- **IC[] collection for Unified Command** — single IC fits >95% of local ops; UC is Type II/I territory
- **Federal cache (TF-State) management** — local depts manage apparatus inventory, not federal cache
- **Full FEMA demob lifecycle** (proposed → reviewed → approved → executing → released) — local depts release apparatus, not demobilize federal resources
- **ICS-205 (comms plan), ICS-207 (org chart graphic), ICS-208 (safety message), ICS-209 (incident status summary)** — these forms appear at Type II/I scale; v4.0 ships only ICS-201 baseline + ICS-203 auto-populated
- **IST coordination workflows** — Incident Support Team is federal-deployment-specific
- **Bulk-deploy mode for 220+ card scenarios** — Type IV/V incidents have 5-20 shore points, not 220
- **Victim cluster linkage** — local rescues are typically 1-2 victims; cluster linkage is a federal collapse-zone pattern
- **Cribbing audit lifecycle** — useful at federal scale; local depts track cribbing informally
- **250+ shore point scale performance work** — local scale fits comfortably in existing data structures
- **Full FEMA Type I/II Command + General Staff** — v4.0 keeps Type III/IV/V presets only

**Verification gate to re-enter:** 10+ municipal fire departments running real Type IV/V incidents (not training) on FieldShore for at least 30 days, with positive feedback on shore point lifecycle, role assignment, and cut tracking. After that gate, Federal Future work lands in v5.2-v5.4+ alongside Phase 4 native-only features.

### Scope Boundaries — What FieldShore IS and IS NOT

**Consensus from IST Plans Chief (#13), Logistics Chief (#14), and multiple reviewers:**

FieldShore is a **shoring operations module** that exports data into the broader ICS ecosystem. It is NOT a replacement for ICS planning tools (D4H, Veoci, WebEOC).

**IN SCOPE — Build and invest:**
Strut finder, shore point lifecycle, cut table, equipment inventory (struts + lumber + plates), apparatus tracking, ICS org chart (internal TF use), operational period snapshots, photos, GPS, QR join, training mode

**IN SCOPE — Build as data export only:**
ICS-203 (auto-populated), ICS-211 (from check-in), ICS-201 (partial), ICS-204 (if division assignments exist), CSV/JSON for all data types.

**For v4.0 specifically (local-first scope, tighter than reviewer recommendation):** Only ICS-201 baseline and ICS-203 auto-populated. ICS-211, 215, 220, 221 are deferred to Federal Future. Rationale: Type IV/V local incidents rarely produce these forms — they appear at Type II/I scale. Building them in v4.0 adds surface area without local-user benefit.

**OUT OF SCOPE — Do not build:**
ICS-202, ICS-205, ICS-206, full planning cycle workflow, general ICS resource management, food/medical vitals/heavy equipment/rigging
