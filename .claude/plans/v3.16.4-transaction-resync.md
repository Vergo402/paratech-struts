# Plan: v3.16.4 — Transaction Resync (#71)

> **Date:** 2026-05-19 (revised after Phase 7 agent review)
> **Type:** PATCH (architectural single-item)
> **Predecessor:** v3.16.3 (shipped 2026-05-19)
> **Successor:** v3.17.0 (local-first defaults + carry-overs)

---

## Context

v3.16.3 deferred [#71](https://github.com/Vergo402/paratech-struts/issues/71) on agent recommendation. v3.16.4 ships the architectural full-fix.

**The bug:** `firebaseSave()` at [app.js:1492](app.js:1492) skips queueing failed writes when `method === 'transaction'`. v3.15.0 added the `offlineTouchedInventory` system to mitigate this, but `markOfflineTouched()` only fires when `txResult.offline === true` (e.g., [app.js:5223](app.js:5223)). Any non-offline failure — validate-rule rejection, permission denied, abort-after-25-retries — falls through to a `logSyncEvent('transaction_failed', …)` and is silently dropped. The local decrement then loses to the next inventory listener snapshot.

**The fix:** extend v3.15.0's `offlineTouchedInventory` system to cover non-offline transaction failures too, and add four safety guards that the v3.15.0 path was missing: mutation-epoch, peer-write guard, `_meta.lastVerifiedAt` audit signal, and bounded retries with diagnostics.

**Why "extend" not "parallel queue" (resolves code-auditor C1):** The first draft of this plan proposed a new `pendingResyncs` queue. That would have raced the existing `offlineTouchedInventory` system, since both target the same `inventory/$itemId.available` field. The plan now treats v3.15.0's mark/filter/flush trio as the single source of truth and adds the missing pieces on top.

## Implementation breakdown

### Component A — Cover non-offline transaction failures

**Current state ([app.js:1488–1499](app.js:1488)):** `firebaseSave`'s catch block routes non-transaction writes to `pendingWrites`, but for transactions it only emits `logSyncEvent('transaction_failed', …)` and drops the write.

**Change:** inside the `else` branch (the transaction failure path), detect inventory-`available` paths and route them to `markOfflineTouched()`:

```js
} else {
  const path = ref.toString().replace(/.*firebaseio\.com/, '');
  logSyncEvent('transaction_failed', { path, error: err.message || String(err) });
  // v3.16.4 #71: catch inventory available-field failures and route through
  // the v3.15.0 offline-touched pipe so the listener and reconnect-flush
  // recover the local value.
  const invMatch = path.match(/^\/departments\/[^/]+\/inventory\/([^/]+)\/available$/);
  if (invMatch && opts && typeof opts.localAvail === 'number') {
    markOfflineTouched(invMatch[1], opts.localAvail);
    logSyncEvent('resync_enqueued_via_failure', { itemId: invMatch[1], localAvail: opts.localAvail });
  }
}
```

**Caller change:** each inventory-`available` transaction must pass `opts.localAvail` to `firebaseSave` so the catch path knows what value to preserve. Add `localAvail` to the `opts` arg at the existing call sites:

- [app.js:5223](app.js:5223) — `deployShorePoint` strut decrement (and L5227, L5233 for extension/plate)
- [app.js:5607](app.js:5607) — `returnInventoryItems` strut increment (and L5611, L5617)
- [app.js:6864](app.js:6864) — `makeAllocateDecrementer` factory output

After the change, BOTH `txResult.offline === true` AND any thrown failure now mark the item touched. The deploy/return sites can then drop their explicit `if (txResult.offline) markOfflineTouched(…)` calls — `firebaseSave` handles it uniformly. (Decision: keep both for belt-and-suspenders; `markOfflineTouched` is idempotent.)

### Component B — Mutation-epoch guard

**Why:** between a mark and the next reconnect-flush, the user may successfully complete another deploy/return on the same item via a normal transaction. The flushed mark would carry an out-of-date `localAvail`.

**Implementation:**

```js
// Module-level
const _itemEpoch = new Map(); // inventoryId -> integer

function bumpEpoch(itemId) {
  if (!itemId) return 0;
  const next = (_itemEpoch.get(itemId) || 0) + 1;
  _itemEpoch.set(itemId, next);
  return next;
}
```

Bump call sites (per code-auditor C9 — at call sites, not inside `updateFunction` which Firebase retries internally):

- [app.js:5223](app.js:5223) — `deployShorePoint` per-item decrement (strut/ext/plate)
- [app.js:5607](app.js:5607) — `returnInventoryItems` per-item increment
- `runDeployTransactions` (~L6905) — per `guards.push` entry, bump before invoking the transaction

Extend `markOfflineTouched(itemId, localAvail, epoch)` to record the epoch at mark-time. Extend `flushOfflineTouchedInventory()` to drop entries whose epoch ≠ current `_itemEpoch.get(itemId)`:

```js
// Inside the flush loop
if (entry.epoch !== (_itemEpoch.get(id) || 0)) {
  logSyncEvent('resync_dropped', { itemId: id, reason: 'epoch_advanced' });
  clearOfflineTouched(id);
  continue;
}
```

This guarantees the flushed value reflects the latest local mutation, not a stale one.

### Component C — Peer-write guard

**Why (code-auditor C3 + devops-resilience #5):** v3.15.0's `flushOfflineTouchedInventory` transaction returns `localAvail` unconditionally. If a peer device's transaction succeeded with `available = 2` while this device's mark carries `localAvail = 4`, the flush will clobber the peer's lower value. The new behavior must drop the flush in that case.

**Implementation:** change the transaction body at [app.js:1038–1041](app.js:1038):

```js
const result = await inventoryRef.child(id).child('available').transaction((v) => {
  if (v === null || v === undefined) return undefined; // peer-deleted; don't materialize
  // v3.16.4: don't clobber a peer's lower value. We only write if Firebase
  // is stale-HIGH relative to our local count. The mark exists because we
  // decremented locally; if the server is already at or below our local
  // count, peer activity already converged us.
  if (v <= localAvail) {
    return undefined;
  }
  return localAvail;
});
```

If `result.committed === false` for the `v <= localAvail` reason (distinguishable by reading `result.snapshot.val()`), emit `logSyncEvent('resync_dropped', { itemId, reason: 'peer_advanced', firebaseAvail: result.snapshot.val(), localAvail })`. Otherwise the existing peer-deleted path remains.

**Resync sets, never deltas (code-auditor C3 invariant):** `localAvail` is always the device's authoritative remaining count, never a delta. If the local count itself is wrong (e.g., a missed listener fire), the flush will still set the wrong value — but the listener gate and peer-write guard combined keep that confined to one device's state and one update.

### Component D — `_meta.lastVerifiedAt` audit signal

Add optional `_meta.lastVerifiedAt` (number, ms epoch) under each `inventory/$itemId`. Set on every successful flush apply via a follow-up `update()`:

```js
if (result && result.committed) {
  // Best-effort audit signal — read-tolerant, no consumer requires it.
  await inventoryRef.child(id).child('_meta').update({ lastVerifiedAt: Date.now() })
    .catch(err => console.warn('[offline-touched] _meta write failed (non-fatal):', err && err.message));
}
```

`database.rules.json` change — scope the validate to the leaf, not the wrapper, so existing items without `_meta` keep passing plain inventory writes (devops-resilience #1 + release-manager #1):

```json
"inventory": {
  "$itemId": {
    ".validate": "newData.hasChildren(['model', 'quantity', 'available'])",
    "_meta": {
      "lastVerifiedAt": {
        ".validate": "newData.isNumber()"
      }
    }
  }
}
```

Verification gate before merge: write an inventory item with no `_meta` (via `confirmAddApparatus`) and a separate item via Excel import — both must pass.

### Component E — Bounded retries + diagnostics

**Why (code-auditor C6):** a misconfigured rule or persistent permission error would cause `flushOfflineTouchedInventory` to retry on every reconnect tick indefinitely. Add a `retries` counter on each touched entry; drop at `MAX_RESYNC_RETRIES = 3` with a diagnostic.

Extend the touched entry schema: `{ localAvail, touchedAt, epoch, retries }`. Increment `retries` on each thrown failure inside the flush loop; clear when committed. At `retries >= 3`, emit `logSyncEvent('resync_dropped', { itemId, reason: 'max_retries' })` and `clearOfflineTouched(id)`.

**Diagnostics events emitted:**

| Event | When |
|---|---|
| `resync_enqueued_via_failure` | `firebaseSave` catch routes a transaction failure into the touched set |
| `resync_applied` | Flush commits a value with `{ drift: localAvail - prevFirebaseAvail, durationMs, fromEpoch }` |
| `resync_dropped` | `reason ∈ { epoch_advanced, peer_advanced, peer_deleted, stale_24h, max_retries }` |
| `resync_failed` | Transaction threw; `{ itemId, error, retries }` |

All events conform to the existing `/diagnostics/sync/` validate rule (requires `ts` + `event`); `logSyncEvent` already sets both.

### Listener-race resolution (code-auditor C2)

**Why:** post-reconnect snapshots arrive through the already-attached listener and are NOT covered by v3.7.0's `firstSnapshotSeen` guard. `applyOfflineTouchedFilter` at [app.js:2455](app.js:2455) protects against pre-flush snapshots, BUT after a successful flush + commit, the listener's next snapshot reflects the new server value — fine. The race is: snapshot arrives BEFORE flush finishes. v3.15.0 already handles this correctly via the filter (the touched set is consulted on every snapshot, not just first). **No new listener gate needed.** The filter is the gate. Code-auditor C2's concern is resolved by the existing v3.15.0 design — the parallel-queue rewrite would have introduced the race; extending v3.15.0 doesn't.

### Per-dept `_syncedItemIds` (code-auditor C5)

**Why:** never-synced items (created offline on first session) routed through plain `pendingWrites` would be subject to APP_VERSION discard on upgrade and to the stale-dept filter's confusing toast.

**Disposition:** **defer to v3.17.0 or later.** v3.15.0's offlineTouched system handles items that have at least one Firebase write — items created entirely offline before any sync still go through the existing `confirmAddApparatus` → `firebaseSave('set', …)` path which queues to `pendingWrites` correctly today. This plan does NOT introduce a `bumpEpoch`/`markOfflineTouched` call on a never-synced item (those paths use `set`, not `transaction`). Document this limitation: "bootstrap of a fully-offline-created inventory item that takes a deploy before its first sync is still handled by `pendingWrites` and remains subject to the v3.16.0 APP_VERSION discard." Confirmed acceptable for v3.16.4 because that combo (offline create → offline deploy → upgrade → reconnect) is a 4-step edge.

### Invariants preserved

- v3.10.1 backup safety net still runs.
- v3.15.0 `makeAllocateDecrementer` v=0 guard remains the first line of defense.
- v3.15.0 `applyOfflineTouchedFilter` continues to gate listener snapshots — no new gate needed.
- `window.disableFirebaseWrites` already honored by `flushOfflineTouchedInventory` ([app.js:1022](app.js:1022)); also honored by the new `_meta.lastVerifiedAt` write because it sits inside the flush function.
- Excel import and `endOperation` cascade unaffected — they use `set()` / per-item paths the new code path doesn't touch.

### Failure-injection driver flow (for verification)

DevTools offline-throttle does NOT exercise the non-offline-failure path. The driver monkey-patches `firebase.database.Reference.prototype.transaction` for refs matching `/\/inventory\/[^/]+\/available$/` (tightened from initial draft per qa-driver finding #1) to force `updateFn → undefined` (uncommitted):

```js
const _origTxn = firebase.database.Reference.prototype.transaction;
const RX = /\/inventory\/[^/]+\/available$/;
firebase.database.Reference.prototype.transaction = function (updateFn, onComplete, applyLocally) {
  if (RX.test(this.toString())) {
    return _origTxn.call(this, () => undefined, onComplete, applyLocally);
  }
  return _origTxn.call(this, updateFn, onComplete, applyLocally);
};
// Restore: firebase.database.Reference.prototype.transaction = _origTxn;
```

Mount via `preview_eval` before each affected flow; restore between flows.
