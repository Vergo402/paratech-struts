## Implementation breakdown

### Item 1 — #97 App not spanning window width
**Reported version:** v3.14.2. Current production: v3.16.2. v3.14.3 already lifted the shell cap (style.css:1668–1670: `:root:not(.force-mobile-view) .app { max-width: none }`).

**Three hypotheses to probe (per qa-driver):**
1. Stale service worker — reporter on cached pre-v3.14.3 bundle.
2. `localStorage.forceMobileView` persisted truthy from a prior toggle.
3. An inner panel is still capped to 1200px and creating the illusion.

**Driver protocol (replaces hand-wavy "investigate"):**
1. `preview_start`. Navigate to local v3.16.2 build.
2. `preview_resize` to 1440×900.
3. `preview_eval` to dump diagnostics in one shot:
   ```js
   ({
     swRegistrations: navigator.serviceWorker.getRegistrations().then(rs => rs.length),
     cacheKeys: caches.keys(),
     forceMobileView: localStorage.getItem('forceMobileView'),
     appWidth: document.querySelector('.app').getBoundingClientRect(),
     viewportWidth: window.innerWidth
   })
   ```
4. If `appWidth.width === viewportWidth` and no `forceMobileView` set → close as "stale SW; document reload-fix in release notes."
5. If `forceMobileView === 'true'` → no code change; add release-notes guidance.
6. If `appWidth.width < viewportWidth` despite both above being clean → identify offending descendant via `preview_eval` walking children for `getBoundingClientRect().width !== parentRect.width`. Then fix.

### Items 2/3/4 — #98 #99 #100 button centering (desktop)
**Root cause:** `.btn-primary` has `width: 100%` (style.css:210) + `max-width: 480px` inside `@media (min-width: 768px)` (style.css:1617). With the cap engaged but no auto margins, the button hugs the left edge of its centered parent.

**Fix — scoped selector (NOT broad `.btn-primary`).** Per mobile-ux and code-auditor: the broad rule breaks the feedback modal Submit/Cancel `flex: 1` row (index.html:715–717), Settings Connect inline form (index.html:324–327), and `.ops-add-sp-btn` flex header (index.html:248–250). The narrow selector targets only screen-level primary buttons:

```css
@media (min-width: 768px) {
  .screen > .btn-primary,
  .screen > * > .btn-primary {
    max-width: 480px;
    margin-left: auto;
    margin-right: auto;
    display: block;
  }
}
```

The existing `.btn-primary { max-width: 480px; }` at style.css:1617 will be removed in favor of the scoped rule above (the cap moves with it).

**Reach:** covers Save Settings (`#screenSettings > * > .btn-primary`), Start New Operation (`#screenOperations > * > .btn-primary`), Find Struts (`#screenSelect > .btn-primary`).

**Skipped (correctly):** Feedback modal Submit, Settings Connect inline button, ops-add-sp-btn flex header, all in-modal action buttons — none are children of `.screen`.

### Item 5 — #101 Add Shore Point modal too tall on desktop
**Fix — Option C** (per mobile-ux): pin modal header + footer, scroll only the body. Survives variable content height; canonical desktop modal pattern; field-safe (gloved users can't hit a scroll target that moves with the whole modal).

**Approach:**
- Refactor `.modal` from "single scrolling container" to a flex column with three rows: `.modal-header` (fixed), `.modal-body` (scroll), `.modal-footer` (fixed).
- The Add Shore Point modal (index.html:431+) may not currently have explicit header/body/footer markers — wrap the form content in a `<div class="modal-body">` and the action buttons in `<div class="modal-footer">` if missing.
- CSS:
  ```css
  .modal { display: flex; flex-direction: column; max-height: 85vh; }
  .modal-header, .modal-footer { flex: 0 0 auto; }
  .modal-body { flex: 1 1 auto; overflow-y: auto; }
  ```
- Apply to all modals — but verify other modals don't regress (they already work; this shouldn't worsen them).

### Item 6 — Legend repositioning (desktop)
**Current:** `<details class="ops-legend">` rendered between SHORE POINTS header and card list, in `renderShorePointCards()` output.
**Target:** Top of left column on desktop, above the drilldown tree. Mobile stays inline.

**Approach — DOM order vs CSS `order:` (per mobile-ux):**
- If the legend is rendered inside `renderShorePointCards()` output (likely deep in the DOM, not a direct child of the grid container), CSS `order:` won't apply — it must be promoted to a sibling of the drilldown tree.
- Driver step: inspect DOM tree of `#activeOpOperations` (or equivalent grid container) in preview. Confirm direct-child relationship.
- If sibling of grid children → CSS `order: -1` + media query gate.
- If not → DOM relocation in JS: render legend into a dedicated `<div id="opsLegendSlot">` at top of left column on desktop, leave inline render on mobile.

### Item 7 — Disable ICS org-chart drag-and-drop on phones
**Media query fix (per mobile-ux):** Use `(pointer: coarse)` alone — NOT `(max-width: 768px) and (pointer: coarse)`. The latter misses iPhone 15 Pro Max in landscape (932px logical width). Pointer-capability is the correct discriminant; phones don't rotate to desktop-pointer.

**Optional tightening:** `(pointer: coarse) and (hover: none)` excludes touch-laptops (which can hover). For FieldShore the broader `(pointer: coarse)` is fine — touch-laptop users likely prefer the mobile-safer interaction model anyway.

**Implementation (per code-auditor R-drag-5):**
- Single module-level flag: `const TOUCH_PRIMARY = window.matchMedia('(pointer: coarse)').matches;`
- Gate BOTH the `draggable` HTML attribute writer AND the `touchstart`/`touchmove` clone handlers behind this flag. Code-auditor specifically flagged that gating only `draggable` while leaving touch handlers attached leaves the bug half-fixed.
- Keep tap-to-pick-and-place + arrow toolbar + per-node modal (Move to / Promote / Demote / Left / Right) functional on touch.
- Re-evaluating the flag on resize is NOT necessary (pointer capability doesn't change at runtime in normal use); document this assumption in code with a one-liner.
