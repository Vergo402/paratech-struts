# Round 2 verified new findings

## 🚨 SAFETY-CRITICAL (added by Round 2)

### S1 — Strut algorithm double-deduction bug
**Severity:** CRITICAL — Safety
**File:** `app.js:2846-2847`
**Root cause:** When a pending shore point is re-evaluated after equipment arrives, the code passes `sp.effectiveLength` (already-deducted opening) as the `requiredLength` argument to `findStrutCombinations` AND ALSO passes `sp.deductions`. The function applies deductions a second time.
**Concrete repro:**
- Create SP with opening 100", header=3.5", footer=3.5" → `sp.effectiveLength = 93`, `sp.deductions = {header:3.5, sole:3.5,...}`
- Equipment arrives. Re-validation runs `findStrutCombinations(93, load, 2, opInv, null, {header:3.5, sole:3.5,...})`
- Function does: `effective = 93 - 7 = 86`
- Algorithm searches for struts that fit 86" opening
- The SP is actually 93" effective — wrong recommendation. May approve struts too short for the actual opening.

### S2 — ACME load table over-reports capacity by 17% at 11 ft
**Severity:** CRITICAL — Safety
**File:** `app.js:32-39` (ACME_LOAD_TABLE), `:101-119` (`getLoadCapacity`)
**Root cause:** Paratech O&M Manual Table 2-7 publishes working loads at every foot 2-12. App stores only 24", 48", 72", 96", 120", 144" — and linearly interpolates between. At 11 ft (132") there's a non-linear cliff in the manual:
- 10 ft (120"): 5,360 lb
- **11 ft (132"): 3,932 lb** ← drops sharply
- 12 ft (144"): 3,830 lb

App's linear interpolation between 120" and 144" returns 4,595 lb at 132".
**Discrepancy: app reports 16.9% higher capacity than Paratech manual at 132".**
**Operational consequence:** A 4,200-lb load at an 11ft ACME strut shows "PASS" in the app (margin +395 lb) while the published Paratech rating is 3,932 lb — load is actually OVER rated capacity by 268 lb.

### S3 — ACME capacity overstated at 2-3 ft
**Severity:** CRITICAL — Safety
**File:** `app.js:32-39`
**Root cause:** App's 24" 4:1 capacity = 21,750 lb. Paratech O&M Manual Table 2-7 at 2 ft = 20,000 lb. App over-reports by 8.75% (1,750 lb).
**Operational impact:** Less likely to cause issues than S2 (short struts aren't usually load-limited), but rescuers cross-checking against the printed manual on-scene get conflicting numbers — erodes trust in the tool.

### S4 — App-bricking sessionStorage bug
**Severity:** CRITICAL — Availability
**File:** `app.js:415`
**Root cause:** `const orgCollapsedNodes = new Set(JSON.parse(sessionStorage.getItem('orgCollapsed') || '[]'));` — top-level, unguarded `JSON.parse`. Corrupt sessionStorage (browser quirk, BFCache restore, manual tampering) throws SyntaxError at script-load time → **app.js fails to load entirely** → app is bricked until user clears site data.
**Concrete repro:** Open DevTools → Application → SessionStorage → set `orgCollapsed` to `{invalid` → reload. App white-screens.

### S5 — Online endOperation doesn't clear localStorage operation
**Severity:** CRITICAL — Data integrity
**File:** `app.js:4221-4237`
**Root cause:** Online path archives the op via Firebase update but doesn't call `localStorage.removeItem('fieldstruts_operation')`. Next reload offline reads stale `fieldstruts_operation` → user sees the just-archived op as "active" again. They may attempt to add shore points or end-op twice.
**Concrete repro:** Online → End Operation → without reload, go offline → reload → archived op resurrected as active.

### S6 — Online-only persistence path means offline reload = stale state
**Severity:** CRITICAL — Data integrity
**File:** `app.js:487` (`persistOperation`) + many call sites in else-branches
**Root cause:** `persistOperation()` early-returns when `db && deptId && opId` is truthy — it never writes to localStorage when online. Most mutation callers also have `if (db && deptId && opId) firebaseSave(...) else safeSetItem(...)` patterns. **No path writes to localStorage when online.** Going offline after online mutations loses any work since the last localStorage write (which could be the original op creation, weeks ago).
**Concrete repro:** Online → create 10 SPs → go offline (airplane mode) → reload → last few SPs missing.

### S7 — Firebase listener wipes local data on dept-ID typo
**Severity:** CRITICAL — Data integrity
**File:** `app.js:994-996, 1037-1039`
**Root cause:** Inventory and apparatus listeners unconditionally overwrite localStorage with whatever Firebase returns, even when the response is empty. Typing a wrong deptId (typo at connect) triggers listeners that fire with empty data → localStorage overwritten with `[]` → going offline loses all data.
**Concrete repro:** Connect to "engine42" with inventory → reconnect to "engin42" (typo, empty in Firebase) → go offline → reload → inventory empty.

### S8 — `confirmAddApparatus` doesn't update local state online (interactive-verified)
**Severity:** CRITICAL — UX
**File:** `app.js:1252-1274`
**Root cause:** Online branch does Firebase-only write. No `localApparatus.push()`, no `closeModal`. Apparatus arrival silently fails when network is queueing writes.
**Concrete repro:** Verified live — Alex's "new apparatus arrives mid-op" scenario fails silently in offline-queued mode.

### S9 — `endOperation()` online same class of bug
**Severity:** CRITICAL — UX
**File:** `app.js:4218-4252`
**Concrete repro:** Verified live — `endOperation()` called with confirm mocked to true, op remained "active", inventory unchanged.

## 🔒 SECURITY-CRITICAL (added by Round 2)

### X1 — Drilldown XSS (CRITICAL, no Firebase write required)
**Files:** `app.js:3543, 3547, 3548`
**Root cause:** `displayName` interpolated raw into span content. `key` interpolated into onclick attribute with only single-quote escape (`"` and `>` not escaped — breaks the attribute).
**Concrete repro:** With active op, "+ Shore Point" → Building = `<img src=x onerror=alert('XSS')>` → save → any user viewing the operation drilldown fires the JS. **Stored XSS, persistent, propagates via Firebase.**

### X2 — Inventory model XSS (CRITICAL, no Firebase write required)
**Files:** `app.js:1462, 1488, 4529-4530, 4536`
**Root cause:** `${name}` interpolated raw from `item.model`. JSON import path performs no validation on model strings.
**Concrete repro:** Settings → Import → choose a `.json` file with `{"type":"plate","model":"<img src=x onerror=alert(1)>",...}`. Inventory tab fires the JS.

### X3 — Command Layout onclick XSS (HIGH)
**File:** `app.js:3779-3783`
**Root cause:** `escapedName` only escapes `'` and `\` (in wrong order — `\` replace runs after `'` replace, double-escaping the inserted backslash). `"`, `>`, `<` not escaped. A building/division/area/group containing `"` breaks the attribute.

### X4 — `escapeHtml` inside `value="..."` is wrong escape function (HIGH)
**Files:** `app.js:1286` (apparatus edit form), `app.js:1371` (group dropdown)
**Root cause:** `escapeHtml` uses `div.textContent = s; return div.innerHTML` which doesn't escape `"` or `'`. Used as attribute value escape, attribute breaks on any value containing `"`.
**Concrete repro:** Apparatus name = `X" onfocus="alert('XSS')` (validateInput keeps `"`) → Inventory → Edit → input renders `<input value="X" onfocus="alert('XSS')">` → autofocus fires JS.

### X5 — `aria-label="…${escapeHtml(sp.label)}…"` (HIGH)
**Files:** `app.js:2826, 2827`
**Root cause:** Same as X4 — escapeHtml in attribute context. Shore point label `X" onmouseover="alert(1)` → hovering edit/delete button fires JS.

### X6 — `sp.deployedStrut.model` rendered raw (HIGH, Firebase-only)
**Files:** `app.js:2838, 2949, 3957`
**Root cause:** No render-time escape on `deployedStrut.model`. Firebase write to set this to `<img src=x onerror=alert(1)>` → all viewers fire JS.

### X7 — No Firebase Auth — config hardcoded in source (CRITICAL)
**File:** `app.js:929`
**Root cause:** Firebase config (apiKey, authDomain, databaseURL) embedded in JavaScript bundle. No `firebase.auth()` call. Database open with anonymous read/write to anyone who views the source. **The fact that "users can XSS each other within a department" is the lighter version of "any internet user can read/write to your Firebase."**

## 🏗️ MULTI-DEVICE RACES (added by Round 2)

### R1 — Stale-dept listener overwrite after switch
**File:** `app.js:983-1064`
**Root cause:** `setupListeners()` re-attaches listeners on dept switch but never `.off()` the old ones. After 5 dept switches: 30 active listeners. Old-dept listeners still fire and write to localStorage with old-dept data. Last writer wins — dept-A data leaks into dept-B view.

### R2 — `activeOperation` full-replace clobbers in-flight edits
**File:** `app.js:1001-1015`
**Root cause:** Op listener does `activeOperation = ops[0]` — full reference replacement. If user is mid-edit on a SP (form open), the form's data references an orphan object after the listener fires. Save writes against the orphan but Firebase update merges field-by-field — concurrent field edits from another device get clobbered last-writer-wins.

### R3 — `orgSwapRoles` and `orgReparentRole` write FULL `roles` map (CRITICAL race)
**Files:** `app.js:2291, 687`
**Root cause:** Both functions write the entire `roles` map / `customRoles` array via `set`. Concurrent edits from two ICs simultaneously assigning different apparatus to roles → last writer wipes the other's changes. **Both devices show "Saved" toasts. Only one assignment survives.**

### R4 — Excel import `set` on `/inventory` root (CRITICAL race)
**File:** `app.js:4462-4470`
**Root cause:** Bulk import writes the entire inventory subtree with `set`. If another device is mid-deploy (decrementing a strut's `available` via transaction), the import overwrites the entire inventory tree → other device's deployment is lost OR creates a phantom inventory row with only `{available: 0}` and no `model`/`system` fields.

### R5 — `pendingWrites` double-write with Firebase SDK retry
**File:** `app.js:560-632`
**Root cause:** App maintains its own `pendingWrites` queue in localStorage. Firebase SDK also has its own offline queue. On reconnect, both flush — same write potentially lands twice. For status flips this is idempotent; for `set` on full subtrees (assignedApparatus) it can resurrect deleted items or wipe concurrent additions.

### R6 — Transaction failures silently dropped
**File:** `app.js:579-583`
**Root cause:** `firebaseSave` catches rejection but explicitly skips transaction methods from being queued. Transaction failures (inventory decrement/increment) on network blip are SILENTLY LOST. Over a 28-day op with hundreds of deploys, inventory drift compounds without any user signal.

## ♿ ACCESSIBILITY (added by Round 2)

### A1 — 40+ `<div onclick>`/`<span onclick>` patterns (CRITICAL WCAG 4.1.2)
**Affected:** Org chart nodes, drilldown items, role grid, lane headers, plate picker options, app chips, list-item rows, section-toggles
**Impact:** Not focusable, not announced as buttons by screen readers, not activatable by Enter/Space, no keyboard alternative. The plate picker, drilldown, role grid, AND org chart drag-drop are all built with non-semantic elements.

### A2 — 8+ contrast failures in light mode (CRITICAL WCAG 1.4.3)
Cutting badge orange-on-yellow ≈ 2.9:1 (fails 4.5:1). Runner badge orange-on-orange ≈ 3.2:1. Returned gray-on-light-gray ≈ 3.9:1. Plus `rgba(255,255,255,0.4)` placeholder text and `text-hint` at 4.46:1 (marginal).

### A3 — 8+ contrast failures in dark mode (HIGH)
`.app-chip`, `.role-badge`, `.qty-btn.active`, `.di-status-pill.strutplaced`: `#42A5F5` on `#1A3050` ≈ 3.1:1 fails AA.

### A4 — No status change announcer for screen readers (CRITICAL WCAG 4.1.3)
Shore-point status transitions (pending → cutting → runner → secured) re-render the card silently. No `aria-live` region announces the change.

### A5 — No modal focus trap (HIGH WCAG 2.4.3)
Tab from last focusable element in modal exits to background page.

### A6 — Background not `inert` when modal open
Screen reader users hear background content; keyboard users can Tab there.

### A7 — Form labels mostly not `for=`-linked (HIGH WCAG 1.3.1)
Most form fields rely on implicit label-by-proximity, not `for=`/`id=` linkage.

### A8 — `confirm()` and `alert()` error patterns (HIGH WCAG 3.3.1)
10 confirms, 19 alerts. Errors not associated with offending input via `aria-invalid` / `aria-describedby`.

## 💾 STORAGE / LIFECYCLE (added by Round 2)

### L1 — `safeParse` corruption silently destroys data
**Files:** `app.js:557, 1068, 1076, 4793`
**Root cause:** Corrupt localStorage → returns fallback array `[]` or null. **User never notified.** They see empty state and assume nothing was saved. May start fresh, destroying their actual operation history.

### L2 — `safeSetItem` quota exceeded silently continues
**File:** `app.js:547-554`
**Root cause:** localStorage full → exception caught → toast shown ("Storage full"). But in-memory state continues to accept changes that aren't being persisted. User keeps making changes, reloads, sees pre-quota state — silent loss of post-quota work.

### L3 — `pendingWrites` >24h silently dropped
**File:** `app.js:597`
**Root cause:** MAX_AGE filter drops queued writes older than 24h. Firefighter offline 25+ hours (dead battery, no signal) loses queued work with only a generic "X changes failed" toast.

### L4 — `pendingWrites` URL path includes old dept after switch
**File:** `app.js:606, 4479-4490`
**Root cause:** `logOut()` clears `pendingWrites`. `connectDepartment()` does NOT. Queued writes carry full URLs with old deptId baked in; they replay against old dept after switch.

### L5 — `archivedOperations` unbounded growth
**File:** `app.js:1017`
**Root cause:** `.on('value', ...)` with no `limitTo`. After 100 archived ops × 200 SPs each = ~16 MB always in RAM. PWA on low-end Android could OOM.

### L6 — `fieldstruts_deptName` read but never written
**File:** `app.js:1683`
**Root cause:** Feedback submission reads `localStorage.getItem('fieldstruts_deptName')` but no code writes that key. Always null in feedback payloads.

### L7 — Device clock used for all timestamps
**Files:** `app.js:2988, 3136, 3249, 3343, 4192, 4196, 4236`
**Root cause:** `new Date().toISOString()` everywhere. Field tablet with drifted clock skews timestamps. Cutting table sort by `cuttingStartedAt` is wrong if multiple devices' clocks differ.

### L8 — ID generation collisions on rapid actions
**Files:** `app.js:1175, 1808, 2505, 3004, 3170`
**Root cause:** IDs like `type_<Date.now()>`, `grp-<Date.now()>`, `i<Date.now()>` lack jitter. Two creations in the same millisecond collide. Other IDs (line 3284: `sp-<Date.now()>-<n>`, line 1263: `+ Math.random()`) are correct — pattern is inconsistent.

## ⚙️ NIMS DOCTRINE (added by Round 2)

**Overall NIMS compliance score: 14/75 = 19%**

### N1 — Missing General Staff (CRITICAL for Type I/II)
**File:** `app.js:657-667` (ICS_ROLES_DEFAULT)
**Root cause:** Default has IC, Safety, Operations. **No Planning Section Chief, Logistics Section Chief, Finance Section Chief.** No PIO, no Liaison Officer. Type I/II USAR ops cannot run without Planning (situation/resources units, demob planning) and Logistics (supply, ground support).

### N2 — "Group" field on shore points is doctrinally wrong
**Files:** `app.js:3116` (SP schema), `app.js:1370` (Group dropdown of apparatus IDs)
**Root cause:** v3.5.0 made the SP Group field a dropdown of apparatus IDs. In NIMS, **Group is a functional command unit** (e.g., "Shoring Group", "Search Group") — NOT a resource. This is the most insidious terminology bug — trained NIMS operators will be confused.

### N3 — No operational period concept
**Root cause:** Operation runs continuously from `startTime` to `endTime`. ICS-202/203/204/205 are all per-period. A Surfside-class incident (56 operational periods × 28 days) cannot be modeled.

### N4 — No after-action / ICS form export
**Root cause:** Archived op view dumps shore points and apparatus. No timeline, no role history, no exportable PDF or ICS forms (ICS-201, 203, 204, 211, 215).

### N5 — No agency tagging on apparatus
**Root cause:** Three "Rescue 1" units from MDFR + Hialeah + FL-TF1 show as identical. No `agency`/`homeDept` field. Multi-agency operations become unreadable.

### N6 — No Unified Command support
**Root cause:** Single `ic` role with id `'ic'` is hardcoded singular. Type I incidents (every Surfside-class collapse) MUST run Unified Command with multiple ICs.

### N7 — `canReparent()` gives Safety authority to modify structure
**File:** `app.js:728-731`
**Root cause:** Safety should not have org-restructuring authority. That's Planning Section Chief's role (specifically Resources Unit Leader). Safety has emergency-stop authority over operations, not staffing structure.

## 🐛 LIFECYCLE BUGS (verified by interactive testing in Round 2)

### V1 — Orphan reference render (HIGH)

**Verified:** `deleteApparatus('mdfr-bc4')` (where mdfr-bc4 is IC) is blocked by confirm() prompt about associated equipment — appropriate behavior. But the prompt doesn't mention "this apparatus is assigned a role (IC)" — user would have to discover separately.

### V3 — Corrupt JSON in `fieldstruts_operation` returns null gracefully

**Verified:** Same root cause as S5/S6 — online path writes Firebase only.

# Single biggest call-to-action

**Before any field use of FieldStruts: fix the strut algorithm capacity over-reporting at 11 ft.** This is the only finding in the entire audit that has a direct line from "app says it's OK" to "rescuer dies." Everything else is fixable in a follow-up. This one is non-negotiable.

The fix is small: 4 lines added to the ACME_LOAD_TABLE constant. Effort: 30 minutes including verification. Risk: trivial — adding data points that align with the published manual makes the app strictly more conservative.

After that: address the data-integrity issues (S5, S6, S7, S8, S9 — the offline/online persistence and listener-wipe bugs) that cause silent data loss. Then the security issues (no auth, multiple XSS classes). Then everything else.
