## Findings

### Finding 1 — H1/#415 deployed-count fix does not reach Cutting Station or the archived-operation viewer
**Severity: Medium (Cutting Station) / Low (PastOperationView — records accuracy only)**

`src/ui/operations/ShorePointCard.tsx:256-259`:
```ts
const capacityFlag = useMemo(
  () => (capacityFlagProp !== undefined ? capacityFlagProp : deployedCapacityFlag(sp)),
  [capacityFlagProp, sp],
);
```
`deployedCapacityFlag(sp)` called with **no second argument** falls back to
`strutLoadShare(sp)` (`reducer.ts:106-107`, divides by the *planned* `groupTotal`) —
exactly the false-SAFE pattern the 2026-07-04 H1/#415 fix closed for `OperationsBoard`
(Board/List/Division/Detail all correctly thread `deployedStrutCount(sp, shorePoints)`
per `OperationsBoard.tsx:1124,1555,1583`).

Two call sites never pass `capacityFlag`, so they hit the un-fixed fallback:
- `src/ui/operations/CuttingStation.tsx:137` (`removed` cards) and `:152` (`sent to
  runner` tail) — both render bare `<ShorePointCard shorePoint={sp} ... />`.
- `src/ui/operations/PastOperationView.tsx:86` — the archived-operation viewer.

**Reachable scenario (CuttingStation):** the cutting/runner/secured phase is
individual-per-card by design (status.ts + the v3.8.0 doctrine this port preserves), so
a 3-Post group can have Post 1 in `cutting` while Posts 2/3 are still `pending` (not yet
strut-placed). `deployedStrutCount` would correctly report 1 standing strut and flag
over-capacity if the load only clears at 3 struts; the CuttingStation fallback instead
divides by the planned `groupTotal` (3) and can show no flag where the board's own
Division/List view shows one — the exact H1 defect, reintroduced on one live fireground
surface.

**PastOperationView** is a permanent incident record; a partial-deploy op archived with
this gap would permanently under-report an over-capacity leg in the record.

The code comment at `ShorePointCard.tsx:251-255` acknowledges this is a fallback and
asserts "never worse than the prior [v3] behavior" — true relative to v3, but that is
not the same as compliant with the H1/#415 fix, which the doctrine brief requires to
"hold." A documented shortcut is still a gap; it should be tracked, not read as closed.

**Fix approach (not implementation):** thread `deployedCount`/`capacityFlag` into
CuttingStation's `removed`/`sent` renders and into `PastOperationView`, the same way
`OperationsBoard` does for its own tiles — the archived op's full `shorePoints` array
is already available in both call sites' parent scope.

### Finding 2 — 3-Post wood auto-fill leaks into T-Shore/Double-T on shore-type switch
**Severity: Spec-deviation (not safety-critical — the error direction is conservative)**

`src/ui/operations/AddShorePointModal.tsx:163-166`:
```ts
function selectShoreType(next: ShoreTypeId) {
  setShoreType(next);
  if (next === '3-post') setDeductions((d) => ({ ...d, ...THREE_POST_WOOD }));
}
```
Comment at line 37-39 states "switching away from 3-Post never resets the choice" as a
deliberate design choice. But the v3.9.1 doctrine (also restated at line 37) is that
**T-Shore/Double-T wood must be an explicit operator choice** — not "whatever 3-Post
happened to leave behind." Operator flow: pick 3-Post (auto-fills 6×6/6×6) → change
mind, switch to T-Shore → the form now silently carries forward a 6×6/6×6 deduction
the operator never chose for a T-Shore.

This is the v3.9.1 regression pattern (auto-filled wood the operator didn't
explicitly pick), just triggered by a cross-type switch instead of an initial default.
It is **not safety-critical**: 6×6 (5.5″) is a *larger* deduction than the T-Shore norm
of 4×4 (3.5″), so the leaked value under-states the available strut length (shorter
searchLength) rather than over-stating it — conservative-direction, not a false-SAFE.
It also doesn't touch `cutLengthInches` (shore-type-fixed, ignores the operator
deduction entirely per #361 doctrine). Still worth a fix: an operator who notices
"6×6" pre-filled on a T-Shore form and doesn't realize why may distrust the tool, or
worse, assume it's an intentional recommendation.

**Fix approach:** clear `headerWood`/`footerWood` back to `NO_DEDUCTIONS` defaults on
any switch *away* from 3-Post (not just leave them stale), or clear on every shore-type
change and re-apply `THREE_POST_WOOD` only when landing on 3-Post — either preserves
the "explicit operator choice" invariant symmetrically.

### Finding 3 — `cutLengthInches` has no floor-at-zero guard; a negative cut length can render on the saw hero
**Severity: Low (narrow reachable window, but the doctrine's own "misleading verdict
copy" category)**

`src/core/shorepoint/reducer.ts:235-238`:
```ts
export function cutLengthInches(sp: ShorePoint): number {
  const lumber = woodHeight(CUT_LUMBER[sp.shoreType]);
  return Math.floor((sp.measurementEighths / 8 - 2 * lumber - WEDGE_DEDUCTION) * 8) / 8;
}
```
No `<= 0` guard, unlike the strut-sizing path (`engine.ts:127`, `Math.floor(exactLength
* 8) / 8 <= 0) return []`). The value feeds `CuttingStation.tsx:73-75`
(`cutEighths`) and `cardParts.ts:76-78`, both piped straight into
`MeasurementValue`/`InchesValue`, whose own doc comment explicitly anticipates and
renders negative values with a sign (`Measurement.tsx:24,53,86`: "may be negative,
e.g. an impossible effective length").

**Reachability:** the strut-sizing engine gates entry to `cutting` status on the
*operator's chosen* deduction (`resolveDeductions(sp)` in `findForShorePoint`), not on
the shore-type-fixed cut lumber. For T-Shore/Double-T (fixed deduction 8.5″: 2×3.5″ +
1.5″ wedge) this can't go negative because the smallest catalog strut (AT 12-15,
collapsed 12″) already exceeds it — any raw opening that reaches `cutting` is ≥ 12″,
giving cut length ≥ 3.5″.

For **3-Post** the fixed cut deduction is 12.5″ (2×5.5″ + 1.5″), which *does* exceed
the smallest strut's 12″ collapsed length. Nothing in `DeductionPicker` locks the
3-Post wood selection to the `THREE_POST_WOOD` auto-fill (confirmed — no
shore-type-aware disabling in `src/ui/quickfind/DeductionPicker.tsx`), so an operator
can manually override a 3-Post point's strut-sizing deduction down from 6×6/6×6.
Worked example: 3-Post, raw opening 12″ (`measurementEighths = 96`), operator
overrides deductions to `none`/`none` (topPlate/bottomPlate none too) — the smallest
AcmeThread strut (collapsed 12″) fits exactly, the point reaches `strutset` → `cutting`.
`cutLengthInches` then computes `floor((12 − 11 − 1.5) × 8) / 8 = floor(-0.5×8)/8 =
−0.5″` (verified by hand: `12 − 2×5.5 − 1.5 = −0.5`), which `cutEighths` passes
straight to the hero's `MeasurementValue` as `−4` eighths → renders **"−1/2″"** on the
saw operator's screen with no warning, no block, no explanation. A cutter facing a
negative number on the one promoted value at the cutting station has no defined
action.

This is a narrow window (near-minimum opening + a manual deduction override against
the 3-Post doctrine default) but it is directly reachable through the UI as shipped,
and it sits squarely in the "misleading verdict copy" category the gate brief called
out — not merely a display nicety, since the cutting-station hero is described in
`CuttingStation.tsx`'s own doc comment as "the one promoted number."

**Fix approach:** floor `cutLengthInches` at 0 (or better, surface an explicit
"cut length invalid — opening too small for standard [4×4/6×6] header+footer" state at
the cutting station rather than a bare negative number), and/or gate the 3-Post wood
override itself (out of scope for this SME pass which is about the length gate, but
worth a UX note for whoever picks this up).

## Verified-Sound

- **ACME (`Table 2-7`) and LongShore (Dec 2019 datasheet) tables** — re-derived
  independently, not just diffed against the pinned test constants (which are the same
  hand-transcription as `tables.ts`, so agreement between them proves no *typo drift*,
  not correctness against the PDF). Cross-checked the documented derivation rule (3:1 =
  floor(4:1 × 4/3), 2:1 = 4:1 × 2 exact) against every row of `ACME_LOAD_TABLE`:
  all 11 rows satisfy it, e.g. 132″: 4:1=3932 → 3932×4/3=5242.67→floor 5242 (matches
  listed 5242); ×2=7864 (matches). For LongShore, the 132″ row (11000/14667/22000)
  breaks the floor-derivation pattern (11000×4/3=14666.67, which would floor to 14666,
  not the listed 14667 — a round, not a floor) — positive evidence this column is a
  genuinely separate published figure rather than a re-derivation, consistent with the
  file's claim that all three LongShore columns are direct from the manufacturer chart.
  Scope limitation: this pass did not re-fetch the source PDFs; confidence rests on
  this internal-consistency check plus the pre-existing v3.5.2 audit trail (17%/8.75%
  and 17.9%/8.3%/5.6% over-reporting fixes, not re-litigated here since the catalog
  values are byte-identical to what that audit corrected).
- **Conservative-floor interpolation (`getLoadCapacity`, `engine.ts:67-94`)** — confirmed
  it returns the *upper* (longer, lower-capacity) row for any length strictly between
  two rows, never interpolates. Confirmed capacity is looked up at `exactLength`
  (unfloored) while selection/display use `searchLength` (floored) — the ⅛″ floor
  never touches the capacity lookup (`engine.ts:111-129`, comment matches code).
- **LongShore unrated zone (>192″/16 ft)** — `isUnratedZone` (`engine.ts:225`) gates on
  `exactLength > 192` (unfloored), only for `system === 'LongShore'`, and is surfaced
  as a deployable warning combo with an explicit `unratedReason` string, never a silent
  drop. `capacityAll`/`totalCapacity` are forced to 0 for unrated combos (no false
  capacity number rides along). Reachability check: LS 1016 (max, 114–198″) + one 67″
  extension reaches up to 265″, well past 192″, so the branch is genuinely exercised in
  the field, not dead code.
- **ACME/LockStroke never reach the table ceiling** — max theoretical reach is AT 56-88
  (88″) + 36″ of Grey-system extensions = 124″, and LK 55-89 (89″) + 36″ = 125″, both
  well under the 144″ table ceiling. The `return 0` branch for out-of-range ACME/
  LockStroke lengths (`engine.ts:76`) is therefore unreachable for these two systems —
  not a doctrine gap (no ACME/LockStroke unrated-zone case is needed), a genuine
  soundness result rather than an absence of investigation.
- **Wood cut-length doctrine (#361)** — `cutLengthInches` (`reducer.ts:235-238`) uses
  `sp.measurementEighths` (raw opening, not the strut-search's post-deduction length),
  `CUT_LUMBER` fixed per shore type (4×4 T-Shore/Double-T, 6×6 3-Post,
  `reducer.ts:222-226`), no plate heights, minus the flat `WEDGE_DEDUCTION` (1.5″),
  floored to ⅛″ — exactly the doctrine. Confirmed it is a genuinely separate code path
  from `effectiveLengthFrom`/`deductionTotalInches` (the strut-sizing deduction, which
  correctly includes `topPlate`/`bottomPlate`), not a shared helper with a branch.
- **Strut-sizing deduction includes plates** — `deductionTotalInches` (`reducer.ts:
  195-202`) sums `headerWood + footerWood + topPlate + bottomPlate`; `effectiveLengthFrom`
  floors only the final result, matching the "⅛″ floor confined to fit/display" rule.
- **qty>4 warning (NEW-3 doctrine)** — `engine.ts:230-246,322-341`: combos requiring
  >4 struts are excluded from normal results but tracked as `bestExceedsCapacityCombo`;
  if the search comes up empty, an explicit `exceedsCapacity` warning combo is
  synthesized with a full reason string (`engine.ts:340`) and no `recommendedQty`/
  `totalCapacity` that could read as a real recommendation (`recommendedQty: 0`). No
  silent rejection.
- **Load share divides by DEPLOYED count (H1/#415), core math + main board surfaces**
  — `strutLoadShareDeployed` (`reducer.ts:130-131`) divides by `Math.max(1,
  deployedCount)`; `deployedStrutCount` (`reducer.ts:115-119`) correctly counts group
  members with `deployedBom != null && status !== 'returned'`, filtered to the same
  `groupId` and non-deleted. `OperationsBoard.tsx` (Board tile line 1124, List rows
  1493/1500, Division view 1457, Detail drawer 1555/1583) all thread this correctly —
  confirmed by reading the call sites directly, not the mocked `shoreSafety.test.ts`
  suite. (Two secondary surfaces do NOT thread it — see Finding 1.)
  Worked check from `reducer.test.ts:472-474`, independently re-derived: estimatedLoad
  34000, `strutLoadShareDeployed(sp, 1) = 34000`, `(sp, 2) = 17000`, `(sp, 0) = 34000`
  (floor-at-1 guard) — all arithmetically correct.
- **Deploy-time gate intentionally uses planned `groupTotal`, not deployed count** —
  `reducer.ts:126-128` comment + `strutLoadShare` (`:106-107`) — correct by design: the
  deploy flow commits one strut at a time and must honor the operator's N-strut intent
  mid-commit, not react to its own partial state. This is a different call site from
  the READ-surface flag (Finding 1's regression is on the read surfaces only).
  Confirmed with test at `reducer.test.ts:494-495,547-548`.
- **3-Post wood auto-fill / T-Shore-Double-T explicit choice (v3.9.1 doctrine)** —
  `SHORE_TYPES` catalog carries no per-type default fields (`plates.ts:73-76`, "the
  v3.9.1 regression" the comment names directly); only `AddShorePointModal.tsx:163-166`
  auto-fills, and only on `next === '3-post'`. Confirmed no other code path auto-fills
  header/footer wood. (The switch-away leak is Finding 2, a narrower issue than a
  blanket auto-fill regression.)
- **`sfIndex` default is 4:1 (most conservative), not silently 2:1** —
  `SP_SAFETY_FACTOR_INDEX = 2` (`reducer.ts:36`) → `row[sfIndex+1] = row[3]` =
  the `load4to1` column in every `LoadRow` tuple `[length, load2to1, load3to1,
  load4to1]`. `QuickFind.tsx` and every shore-point read path go through
  `findForShorePoint`, which hardcodes this constant — there is no UI control that
  silently defaults to a looser factor. This was the one check that could have moved
  the verdict to FAIL; it does not.
- **USACE/FEMA shore-type catalog** — `SHORE_TYPES` (`plates.ts:77-81`) covers
  Vertical T-Shore (1 strut/shore), Double-T Vertical Shore (2), 3-Post Vertical Shore
  (3) — matches the doctrine's named configurations; `strutsPerShore` correctly drives
  card-count multiplication in `AddShorePointModal.tsx` (`totalStruts = qtyNum *
  strutsPerShore`).
