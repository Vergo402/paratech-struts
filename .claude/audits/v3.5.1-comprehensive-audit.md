# FieldShore v3.5.1 — Comprehensive Audit

**Date:** 2026-05-14
**Scenario:** Surfside-scale collapse. 41+ shore points across 12-story North/South Tower, 21 apparatus from 5+ agencies (MDFR, Hialeah, Pembroke Pines, Coral Gables, Fort Lauderdale + FL-TF1, PA-TF1, OH-TF1), multi-day operation with shift rotations.
**Reviewers:** 8 role-based agents — Battalion Chief (IC), Operations Section Chief, Rescue Captain (entry team), USAR Task Force Leader, Cutting Table Lead, Safety Officer, Shoring Team Member, Senior Full-Stack Engineer. Plus interactive stress test by the lead engineer driving the app at scale.

**Total raw findings:** 110+. After cross-reviewer deduplication: 67 unique issues.

---

## Executive Summary

The app is **competent at strut selection and shore-point tracking** — its core domain. The math, the plate picker, the offline-capable PWA pattern, and the role-based view system are all solid.

The app is **not yet ready for Type I/II USAR command** without addressing 14 CRITICAL findings. The dominant failure modes are:

1. **Data loss on Firebase reconnect.** Local-only operations and inventory are silently destroyed when listeners fire with empty server snapshots. (5 reviewers flagged this independently.)
2. **Section-button UX dead-end.** v3.4.1's collapsed-by-default change broke the "Assign Apparatus" flow — clicking does nothing visible. (3 reviewers confirmed via code reading; reproduced live.)
3. **Status transitions silently fail offline.** `updateShoreStatus` writes only to Firebase when online+queued; UI doesn't reflect change until reconnect. (Confirmed via reproduction.)
4. **Equipment doesn't release on backward state transitions.** Cutting → strutplaced doesn't return the strut to inventory. Inventory drifts. (Ops Chief, Senior Eng.)
5. **No accountability infrastructure.** No PAR, no apparatus check-in/demob timestamps, no role history, no operational-period concept, no exportable after-action report. (Battalion Chief, Safety Officer, USAR Task Force Leader.)
6. **No emergency / stop-work / mayday button.** Safety Officer has no in-app channel to halt unsafe ops. (Safety Officer.)
7. **No multi-agency data isolation.** All task forces share a `deptId` with shared trust; no per-write auth or attribution; non-transactional `.set()` calls silently clobber concurrent edits. (USAR Task Force Leader, Senior Eng.)
8. **XSS attack surface.** User-controlled strings in drilldown labels, apparatus/plate names from XLSX import, and the `renderCommandLayout` onclick handler all bypass `escapeHtml`. (Senior Eng.)

# Findings by Theme

## A. Data Integrity & Firebase Sync (10 findings)

### A1 — CRITICAL — Firebase listener overwrites local data with empty arrays on first connect
**Source:** Interactive F1; BC carry; USAR M8; Senior Eng C1, H4
**Files:** `app.js:983-1064` (`setupListeners`), specifically `inventoryRef` listener at ~993, `apparatusRef` at ~1036, `operationsRef` at ~1001
**Root cause:** Each listener unconditionally calls `safeSetItem('fieldshore_xxx', JSON.stringify(snap.val() || {}))`. On first connect to an empty/new dept, `snap.val()` is null, so `{}` becomes `[]` after `Object.entries()`, and localStorage is overwritten.
**Worst case:** USAR task force sets up app on the plane (apparatus + inventory locally), connects to operation's deptId at staging — all their work vanishes. The active operation case (`operationsRef` listener) has no recovery path because the operation only exists in localStorage.
**Fix:** On listener first-fire, if `snap.exists() === false` AND local data exists, push local data to Firebase BEFORE accepting empty snapshot. Add a "first-fire guard" flag per listener.

### A2 — CRITICAL — `updateShoreStatus` doesn't update local state when online+queued
**Source:** Interactive F3; USAR M10; Senior Eng C4; Shoring FF3 (extends to `deployShorePoint`)
**Files:** `app.js:3322-3362` (`updateShoreStatus`); same pattern in `deployShorePoint` at 3256-3287
**Root cause:** When `db && deptId && opId` is truthy, ONLY `firebaseSave` is called. If the WebSocket is offline or the write is queued, `activeOperation.shorePoints[i].status` is never mutated and the UI doesn't reflect the change.
**Worst case:** Operator on Floor 8 with weak cellular taps "→ Cutting" repeatedly thinking it's broken. Each tap queues another `firebaseSave`. On reconnect, multiple transitions fire.
**Fix:** Always `Object.assign(member, updateData)` locally THEN call `firebaseSave`. Let the listener reconcile.

### A3 — CRITICAL — Service worker leaves stale assets after deploy during active op
**Source:** Senior Eng C5
**Files:** `sw.js:36-47` (fetch handler); `app.js:4840-4844` (controllerchange guard)
**Root cause:** Stale-while-revalidate returns cached `index.html`/`app.js` immediately. Reload prompt is suppressed when `activeOperation` is set. So an in-progress operation never picks up bug fixes — even when a new SW is installed.
**Fix:** Network-first for `index.html` and `app.js` (fallback to cache on network failure). Non-dismissible banner when new SW waiting between operations.

### A4 — CRITICAL — Setting `.set()` on shared structures silently clobbers concurrent writes
**Source:** USAR M2
**Files:** `app.js:1751` (`assignedApparatus`), `app.js:687` (`customRoles`), `app.js:2290` (reparent writes the whole `roles` object)
**Root cause:** Multiple devices simultaneously updating org chart write the FULL object via `.set()`. Last writer wins; concurrent changes vanish.
**Fix:** Use `.update({path: value})` for individual fields. For composite changes, use `.transaction()`.

### A5 — HIGH — No `.off()` calls; `setupListeners` leaks on every dept switch
**Source:** Senior Eng H1
**Files:** `app.js:983-1064`
**Root cause:** Each `connectDepartment()` re-attaches all listeners without detaching prior ones. Hot-swap dept = N×listener firing per change.
**Fix:** Track refs in module state; `.off()` before re-attaching.

### A6 — HIGH — `customRoles` / `assignedApparatus` not normalized on read from Firebase
**Source:** Senior Eng H2
**Files:** `app.js:1006` (operations listener)
**Root cause:** RTDB returns arrays-with-non-numeric-keys as objects. `customRoles` is read as raw `...op` spread. Subsequent `.find()`/`.filter()`/`.push()` calls throw "is not a function".
**Fix:** Normalize at read: `if (op.customRoles && !Array.isArray(op.customRoles)) op.customRoles = Object.values(op.customRoles)`. Same for `assignedApparatus`, `shorePoints`, etc.

### A7 — HIGH — `confirmStartOp` online doesn't set `activeOperation` until listener round-trip
**Source:** Senior Eng H5
**Files:** `app.js:2977-3014`
**Root cause:** Online path writes to Firebase and returns. `activeOperation` stays null. User can tap "Add Shore Point" before listener fires → modal early-returns.
**Fix:** Set `op.id = newRef.key` and `activeOperation = op` optimistically.

### A8 — HIGH — `pendingWrites` replay can resurrect since-deleted entities
**Source:** Senior Eng H6
**Files:** `app.js:588-632` (`flushPendingWrites`)
**Root cause:** Offline: update apparatus name, delete apparatus, reconnect. The pending update writes succeed against the path → apparatus reappears.
**Fix:** On delete, prune `pendingWrites` whose path falls under the deleted entity.

### A9 — MEDIUM — `pendingWrites` only persists on Firebase reject, not on transient network loss
**Source:** USAR M11
**Files:** `app.js:580-583`
**Root cause:** If Firebase accepts the write but the device loses network 50ms later before the SDK acknowledges, the write is lost. Persistence isn't enabled (`firebase.database().setPersistenceEnabled(true)` not called).
**Fix:** Enable Firebase persistence on init.

### A10 — MEDIUM — `returnInventoryItems` mutates local externalEquipment in addition to the Firebase transaction
**Source:** Senior Eng M3
**Files:** `app.js:4145-4149`
**Root cause:** Local `available++` runs unconditionally, then Firebase `.transaction()` adds another +1 via listener. Under rapid clicks, listener races overwrite some local mutations.
**Fix:** Trust Firebase as source of truth; don't mutate local in the Firebase branch.

## B. Equipment / Inventory Lifecycle (5 findings)

### B1 — CRITICAL — Backward state transitions don't release equipment
**Source:** Ops C1
**Files:** `app.js:3322-3356` (`updateShoreStatus`)
**Root cause:** Cutting → strutplaced flips status but doesn't call `returnInventoryItems()`. `deployedStrut`, `deployedExtensions`, `deployedPlates` stay set. Inventory `available` count is stuck.
**Worst case:** IC thinks Rescue 1 has 2 of 37-58s left; really has 4. Next deployment fails "available > 0" check, runner sent for nothing.
**Fix:** On backward transition past `strutplaced`, prompt "Pull this strut from the wall?" → if yes, return inventory and null deployed fields.

### B2 — CRITICAL — `cuttingStartedAt` and `cutLength` clobbered on re-entry to cutting
**Source:** Ops C2
**Files:** `app.js:3339-3344`
**Root cause:** Every transition to `cutting` resets both fields. Bouncing back and forth wipes history; phantom mismatches between expected and actual cut on cards never re-cut.
**Fix:** Only set `cuttingStartedAt` if not already set (or append to attempts array). Don't recompute `cutLength` if deductions haven't changed.

### B3 — HIGH — Pending shore points have no "needed model" tag, no aggregate "what we're waiting on"
**Source:** Ops H1
**Files:** `app.js:2842-2854`, `deployPendingShorePoint` line 3105
**Root cause:** Pending SPs have null `deployedStrut`. No way to encode "needs an AT 37-58" so a runner/logistics can fulfill.
**Fix:** Add `neededModel` field populated from the find-result that triggered pending. Render "Pending Equipment Needs" rollup card on Command view.

### B4 — MEDIUM — `endOperation` resets ALL inventory, not just this op's
**Source:** Senior Eng M6
**Files:** `app.js:4244-4246`
**Root cause:** `for (const item of localInventory) item.available = item.quantity;` — resets globally. Multi-op scenarios (schema allows it) lose tracking.
**Fix:** Compute deployments from `activeOperation.shorePoints`; only reset those.

### B5 — MEDIUM — External equipment edit overwrites available count
**Source:** USAR M4
**Files:** `app.js:2411-2417`
**Root cause:** Edit uses `.set()` of the whole record. Concurrent edits from two devices clobber the available count.
**Fix:** `.update()` user-edited fields; `.transaction()` on `available` if quantity changes.

## C. ICS / NIMS / Multi-Agency (8 findings)

### C1 — CRITICAL — Apparatus has no agency/home-department tag
**Source:** BC C1
**Files:** `app.js` apparatus schema (no `agency` field anywhere)
**Root cause:** Single `taskForce` string on operation only. Three "Rescue 1" units from three agencies show as identical.
**Fix:** Add `agency`/`homeDept` field per apparatus. Color-code badges. Disambiguate in `getApparatusName`.

### C2 — CRITICAL — Org chart cannot represent Type I/II ICS structure
**Source:** BC C2; Safety S4
**Files:** `app.js:657-667` (`ICS_ROLES_DEFAULT`)
**Root cause:** Default has 9 roles: IC, Safety, Operations, Entry, Rescue, Shoring, Runner, Cutting, Wood. Missing Command Staff (PIO, Liaison), General Staff (Planning, Logistics, Finance), Branches, Divisions, Groups, Strike Teams.
**Fix:** Ship NIMS-doctrine presets — "Working Fire (Type IV/V)", "USAR Task Force (Type III)", "Major Collapse (Type I/II)". Add `roleType` field (Branch/Division/Group/Strike Team) for correct rendering.

### C3 — CRITICAL — No operational period concept
**Source:** BC C3; Safety S8
**Files:** Searched — no `operationalPeriod`, `opPeriod`, `shiftChange`, `handoff` references
**Root cause:** Operation runs continuously from `startTime` to `endTime`. No period boundaries. ICS-202/203/204/205 reset each period — current app can't snapshot.
**Fix:** Add `operationalPeriods[]` with `{num, start, end, briefingTime}`. Snapshot role assignments and SP statuses at boundary. Show "OP 4 (1900-0700)" on Command view.

### C4 — CRITICAL — No after-action report / ICS-201 export
**Source:** BC C4
**Files:** `app.js:4218-4252` (`endOperation`); `app.js:2932` (archived render)
**Root cause:** Archived op renders shore points only. No timeline, no role history, no apparatus log, no export.
**Fix:** `exportOperationReport()` — XLSX/PDF dump of roster, role assignments by op period, SP timeline, apparatus log, external ledger. Hook into `endOperation` and offer mid-op too.

### C5 — CRITICAL — Shared `deptId` = no data isolation between task forces
**Source:** USAR M1
**Files:** `app.js:983-1064`, login/connect flow
**Root cause:** Single tenant per dept. FL-TF1 either joins MDFR's dept (writes contaminate MDFR's data) or stays in their own (can't see MDFR's op).
**Fix:** Per-record `agency` tag; security rules; subscribe-to-host-op pattern with own-agency writes.

### C6 — CRITICAL — No auth, no audit attribution
**Source:** USAR M3
**Files:** `app.js:927-958` (`initFirebase`, anonymous); `app.js:4774` (deptId in localStorage)
**Root cause:** Database open with anonymous read/write. `firebaseConfig` hardcoded in source — visible to anyone with browser dev tools. No write carries `changedBy` / `deviceId` / `timestamp`.
**Fix:** Firebase Anonymous Auth + per-device UID. Security rules. Every write decorated with `{by, at}`. At minimum: device UUID at install + write decorator.

### C7 — HIGH — Safety role is locked to IC; cannot delegate Assistant Safety Officers
**Source:** BC H4
**Files:** `app.js:744`
**Root cause:** Hard lock `if (child.id === 'safety') return;`. Prevents Branch-level Assistant Safety Officers on Type I incident. Also no support for Unified Command (multiple co-ICs).
**Fix:** Allow Safety reparent with confirmation. Support Unified Command mode.

### C8 — HIGH — Apparatus check-in / demob has no timestamps
**Source:** BC H1; Ops M2; USAR M6
**Files:** `assignedApparatus[]` is a flat ID array; `removeApparatusFromOp` deletes outright
**Root cause:** No `arrivedAt`/`assignedAt`/`demobedAt` fields. ICS-211 (Check-in List) is a NIMS form. Removing loses history.
**Fix:** Convert `assignedApparatus` to objects `{id, arrivedAt, assignedAt, demobedAt, status}`. Add "Demobilize" button preserving history.

## D. Safety / Accountability (7 findings)

### D1 — CRITICAL — No PAR (Personnel Accountability Report) mechanism
**Source:** Safety S1; BC H3
**Files:** `app.js:3723-3727` (headcount), `app.js:3560-3608` (dashboard)
**Root cause:** Counter is apparatus-based, not personnel-based. No `crewSize` or `crew[]` on apparatus. No per-SP `personnelOnsite[]`.
**Worst case:** Secondary collapse. IC asks "How many bodies inside?" — app can't answer.
**Fix:** Add `crewSize` (default by type) and `crew[]` to apparatus. PAR dashboard tile: total / inside / accounted-for with red flag on mismatch.

### D2 — CRITICAL — No emergency / stop-work / mayday button
**Source:** Safety S2
**Files:** Not present
**Root cause:** ISO authority to halt unsafe ops requires a UI channel. None exists.
**Fix:** Persistent red STOP WORK FAB in Safety/IC role views. Writes high-priority record; pushes in-app banner to all devices on the dept; freezes status-transition buttons until IC clears.

### D3 — CRITICAL — No hazard log
**Source:** Safety S3
**Files:** Not present
**Root cause:** No data model for hazards. Confined-space, secondary-collapse zones, Florida heat (which killed crews to exhaustion at real Surfside), HazMat — none can be recorded.
**Fix:** `/operations/{opId}/hazards[]` with `{type, location, severity, reportedBy, reportedAt, mitigations[], cleared}`. Red banner on affected area cards.

### D4 — HIGH — Span warning only fires over 7; misses NIMS optimal/wasteful
**Source:** BC H2; Safety S6
**Files:** `app.js:3693-3694`
**Root cause:** Single threshold (>7). NIMS optimal 5, max 7, wasteful <3 (filled).
**Fix:** Yellow at 6-7, red at 8+, blue at <3 (filled). Display count: "Ops · 9 reports ⚠".

### D5 — HIGH — Stale shore points have no visual indicator anywhere
**Source:** Ops H3; Safety S9; CutTable M2
**Files:** `app.js:2820-2895` (SP card render); `app.js:3856` (cut table)
**Root cause:** Timestamps captured (`createdAt`, `deployedAt`, `cuttingStartedAt`) but never compared to `Date.now()` in render. No staleness threshold.
**Fix:** On every render, compute age. Show "in this status for Xh Ym" under status pill. Red ring for pending>2h, cutting>1h, runner>30min.

### D6 — HIGH — Strut Placed visually equivalent to Secured (fall hazard)
**Source:** Safety S7
**Files:** `style.css:577, 580, 591-596`
**Root cause:** `strutplaced` (blue) vs `secured` (green) — color only. Built-but-unsecured is a personnel fall hazard.
**Fix:** Hatched diagonal pattern or ⚠ UNSECURED overlay on non-secured/returned cards past `process`. Lane header for `strutplaced` carries ISO icon.

### D7 — MEDIUM — Safety role default view = same as IC; no dedicated dashboard
**Source:** Safety S10
**Files:** `app.js:659` (`suggestedView: 'command'`); `app.js:2076-2078`
**Root cause:** Safety role selects "Command" view — same as IC.
**Fix:** Build `'safety'` view: PAR (D1), Hazards (D3), Stale SPs (D5), Span violations (D4), Unsecured count (D6), Stop-Work button (D2).

## E. Field Use / Gloves / Recovery (12 findings)

### E1 — CRITICAL — Section-button actions silently fail in collapsed state (F2 confirmed)
**Source:** Interactive F2; Ops C3; Senior Eng M7
**Files:** `app.js:1722` (`showAssignApparatus`); `app.js:3370` (sectionCollapsedState default)
**Root cause:** v3.4.1 set all four sections collapsed by default. `showAssignApparatus` writes innerHTML into `#assignedApparatusList` which is inside `#sectionApparatus` (display:none). User taps → nothing happens. (Note: `showAddExternal` and `showAddIndividual` open MODALS so they actually work — only `showAssignApparatus` is broken.)
**Fix:** `showAssignApparatus` must auto-expand the Apparatus section before rendering: `if (sectionCollapsedState['apparatus']) toggleSection('apparatus');`. One-line fix.

### E2 — CRITICAL — No `visibilitychange`/`pageshow` handler; dropped phone loses form drafts
**Source:** Shoring FF1
**Files:** `app.js:4744-4767` (only `click` and `keydown` listeners)
**Root cause:** Phone auto-locks → iOS Safari may discard JS context. Modal closes on resume; user re-enters from scratch.
**Fix:** Persist shore point form draft to localStorage on every `input` event. On `pageshow`/init, if draft exists, surface "Resume Floor 4-C-2 measurement?" toast.

### E3 — CRITICAL — No undo on irreversible status transitions; no Deploy confirmation
**Source:** RC C1; Shoring FF2
**Files:** `app.js:3322` (`updateShoreStatus`); `app.js:3964` (`sendToRunner`); `app.js:379` (deploy button)
**Root cause:** Status advance and Send to Runner have no undo or preview. Deploy debounces 2s but no confirmation. `confirm()` and `delete` exist but transitions don't.
**Fix:** Add undo toasts (use existing `undoReparent` pattern at line 757). For Deploy: show strut+length+source as "Tap to confirm" overlay for 2s. For status advance: "Sent to Runner — Undo" toast for 8s.

### E4 — CRITICAL — Native `confirm()` dialogs throughout the app
**Source:** RC C3
**Files:** `app.js:821, 867, 878, 1201, 1318, 2452, 2962, 4119, 4219, 4480` (10 sites)
**Root cause:** Native confirm sits dead-center, tiny OK/Cancel, hard to differentiate by feel with gloves.
**Fix:** Custom confirm sheet anchored bottom (thumb reach), 56px buttons, color-coded (red = destructive).

### E5 — HIGH — Long-press for reparent triggered by water on screen
**Source:** Shoring FF4
**Files:** `app.js:2163-2174` (orgLongPressTimer)
**Root cause:** Static water droplet on glass = continuous touch. 500ms timer fires → reparent mode silently arms. Vibrate doesn't transmit through Nomex gloves.
**Fix:** Require >8px initial movement before reparent mode arms. Or two-finger trigger. Or full-screen visual overlay during long-press.

### E6 — HIGH — Status badges undersized + color-only differentiation
**Source:** RC H1; Shoring FF9; Safety S7 (overlap with D6)
**Files:** `style.css:582-596` (status-badge); `style.css:658` (status-pill)
**Root cause:** 14px badge text, 12px pill text. Cutting yellow and Runner orange visually similar. Color-only fails for ~8% colorblind men.
**Fix:** Leading glyphs per status (⏳/🔵/🟦/✂/→/✓/✕). Bump badge to 16px. Color + shape + text.

### E7 — HIGH — View switcher buttons under 44px
**Source:** RC H2
**Files:** `style.css:669`
**Root cause:** 36-40px buttons. Mis-tap lands on wrong tab; content changes instantly.
**Fix:** `padding: 14px 4px` to hit 48px.

### E8 — HIGH — Quick Find can't deploy; must re-enter measurement in Operations
**Source:** RC H3; Shoring FF6
**Files:** `app.js:277-295` (`runQuickSelect`); `app.js:3075` (`findForShorePoint`)
**Root cause:** Quick Find result has no "Deploy" path. Must navigate to Operations → New Shore Point → re-enter measurement + load + deductions + plates + find → deploy. 8+ extra taps.
**Fix:** Add "Deploy this" button on Quick Find result when `activeOperation` exists. Opens Add Shore Point modal pre-filled.

### E9 — HIGH — Cut table actual-cut input cramped + disappears
**Source:** RC H4; CutTable H1
**Files:** `app.js:3920-3931` (cut table card render)
**Root cause:** Input `#actual-${spId}` only visible when `mode === 'active'`. After Mark Cut Done, the input is replaced — `sendToRunner` reads `#actual-${spId}` (line 3968) but element is gone. Cuts go to runner with no actual recorded.
**Fix:** Keep input visible on done state; or snapshot input value when transitioning to done.

### E10 — HIGH — Measurement entry is three fields for one tape reading
**Source:** Shoring FF5
**Files:** `index.html:398-428` (spFeet, spInches, spFraction); `app.js:1378` (`getMeasurementInches`)
**Root cause:** 7'4-1/2" requires 6+ tap/keystrokes including iOS picker wheel for fraction.
**Fix:** Single text input parsing `7'4-1/2"`, `7 4 1/2`, `88.5`, etc. Keep fields as fallback.

### E11 — HIGH — Inventory quickview close (×) under 44px
**Source:** RC H5
**Files:** `style.css:875-881`
**Root cause:** 36px square — only Apple HIG violation among modal closes (others use full-width buttons).
**Fix:** `min-width: 44px; min-height: 44px; padding: 12px`. One-line.

### E12 — MEDIUM — No "yours" lane to find shore points YOU just created
**Source:** Shoring FF7
**Files:** No user/createdBy field
**Root cause:** With 41+ SPs on screen, shorer can't find their own card after deploy without remembering the label.
**Fix:** Track `_lastDeployedSpId` per session in localStorage. Render "Recent (you)" lane at top of Operations view.

## F. Runner Workflow (4 findings)

### F1 — CRITICAL — No runner identity; no in-flight queue; no recall path
**Source:** Ops H2; RC C2; CutTable M1
**Files:** `app.js:3964-3994` (`sendToRunner`)
**Root cause:** "Runner" status is a flag. No `runnerId`/`runnerName`/`runnerStartedAt`/`runnerETA`. Two runners can leave with the same cut; no recall.

### F2 — HIGH — Entry team has no "cut is in transit" cue
**Source:** CutTable H3
**Files:** `app.js:2880-2884`
**Root cause:** Status flips silently. No toast, no banner, no flash. Captain busy with another SP misses the transition.
**Fix:** Wire toast in `renderOperations` for SPs newly transitioned to `runner`. Or add "Incoming Cuts" mini-panel on Ops view.

### F3 — HIGH — Grouped shore points render as separate cards on cut table
**Source:** CutTable C1
**Files:** `app.js:3856-3888` (`renderCutTableView`)
**Root cause:** Double T-Post pair (groupTotal:2) shows as TWO "Ready to Cut" cards. Cutter slaps one cut on a runner, doesn't realize they owe two more sticks for the same group.
**Fix:** Dedupe by `groupId`. One card per group: "T-POST PAIR — 2 cuts" or "3-POST — 3× 78″".

### F4 — HIGH — Cut table sort is age-only; no priority/location grouping
**Source:** CutTable C2
**Files:** `app.js:3858-3864`
**Root cause:** FIFO by `cuttingStartedAt`. Floor 10 critical-overhead emergency sits behind Floor 2 non-critical from 45 min ago.
**Fix:** Section by Floor/Division first (closest to entry team first), then by time. Priority pin button.

## H. Security (4 findings)

### H1 — CRITICAL — XSS via drilldown labels (building/division/area/group)
**Source:** Senior Eng C2
**Files:** `app.js:3537-3548` (`renderDrilldownForLevel`)
**Root cause:** `key` is user-controlled string. Interpolated raw into both `<span>` content and `onclick` attribute. A user typing a building name like `</span><img src=x onerror=alert(...)>` triggers script execution for every other user.
**Fix:** `escapeHtml(displayName)` for content. `data-` attributes + event delegation for onclick.

### H2 — CRITICAL — Double-escape bug in `renderCommandLayout` breaks JS + leaks HTML
**Source:** Senior Eng C3
**Files:** `app.js:3779-3784`

**Fix:** Replace inline onclick with `data-level/data-value` + delegated listener. Always `escapeHtml(name)` for content.

### H3 — HIGH — XSS via apparatus/plate `model` strings from XLSX import
**Source:** Senior Eng H3
**Files:** `app.js:1462`, `1488`, `2699`, `4536`
**Root cause:** Several render sites use raw `${name}` / `${item.model}`. XLSX import accepts user-controlled cells.
**Fix:** `escapeHtml()` at every render site.

### H4 — CRITICAL — No auth; Firebase config hardcoded in source (overlap with C6)
