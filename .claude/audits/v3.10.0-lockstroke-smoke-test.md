# F-4B-14 — LockStroke Per-Strut Extension Compatibility — UI Smoke Test

**Finding source:** `.claude/audits/v3.8.2/SUMMARY.md` line 91 — "LockStroke extension compatibility UI enforcement needs verification."

**Algorithm origin:** v3.5.2 fixed the algorithm with per-strut `LOCKSTROKE_EXTENSIONS` map at [app.js:31-39](../../app.js#L31). v3.8.2 audit flagged that end-to-end UI verification was incomplete.

**Verified in:** v3.10.0 (this commit / 2026-05-16).

## What the map encodes

```javascript
const LOCKSTROKE_EXTENSIONS = {
  'lk-19-25': [6, 12],
  'lk-30-48': [6, 12, 24],
  'lk-55-89': [6, 12, 24, 36],
};
```

`findStrutCombinations` at `app.js:198-201` reads the strut-specific list first; only falls back to the shared `EXTENSIONS[system]` when the strut is non-LockStroke.

## Verification procedure (algorithmic)

Driven from the live preview during v3.10.0 testing. Synthesizes a worst-case inventory where the *wrong* extension is present and confirms it is not offered.

```javascript
// In the running app's DevTools console:
const inv = [
  { id: 'inv-strut-1925', type: 'strut', model: 'LK 19-25', system: 'LockStroke', apparatus: 'app1', available: 5, quantity: 5 },
  { id: 'inv-ext-24',     type: 'extension', length: 24, system: 'LockStroke', apparatus: 'app1', available: 5, quantity: 5 }
];
const results = findStrutCombinations(48, 0, 2, inv, null, null);
const offending = results.filter(r => r.strut.model === 'LK 19-25' && r.extensions.includes(24));
console.log({ offending: offending.length, allLK1925: results.filter(r => r.strut.model === 'LK 19-25') });
```

Expected: `offending === 0`. Any non-zero count is a regression.

## Result — 2026-05-16

```
{
  "lk1925Exts": [6, 12],
  "lk5589Exts": [6, 12, 24, 36],
  "uniqueToLK5589": [24, 36],
  "totalResults": 0,
  "lk1925ResultsWithDisallowedExt": 0,
  "allResultsForLK1925": []
}
```

LK 19-25 with a 24" extension in inventory returns zero results. Per-strut filter is enforced as intended. No regression.

## UI cross-check

The renderer at `app.js:533-547` only paints what `findStrutCombinations` returns. Since the algorithm rejects disallowed strut + extension pairs, the UI cannot offer them. This holds for both the Quick Find tab and the Add-Shore-Point modal (both use the same `findStrutCombinations` + `renderResults` pipeline).

## Re-run cadence

Re-execute the procedure above whenever any of the following change:
- `LOCKSTROKE_EXTENSIONS` map at `app.js:31-39`
- `findStrutCombinations` extension-lookup branch at `app.js:198-201`
- Any new LockStroke strut model is added to `STRUTS`

Adding a row to this file with the new date + observed outputs is sufficient.

# F-4B-13 — Quick Find Input Debounce — Closure Note

**Finding source:** `.claude/audits/v3.8.2/SUMMARY.md` line 163 — recommended adding a 150ms debounce to Quick Find input handlers, citing observable recompute on 200+-item inventories.

**Closure decision:** Audit premise does not hold in v3.10.0.

## Evidence

- `index.html:73, 77, 81` — Quick Find measurement inputs (`qfFeet`, `qfInches`, `qfFraction`) call only `updateDeductionSummary('qf')` on input/change.
- `index.html:166` — the heavy `runQuickSelect()` (which calls `findStrutCombinations`) is invoked by an explicit "Find Struts" button.
- `app.js:399-416` — `runQuickSelect` is the only entry point for `findStrutCombinations` in the Quick Find flow; not wired to live input events.
- `app.js:5623` — `updateDeductionSummary` reads measurement + deductions and updates a single DOM summary span. No strut search. Trivial cost.

There is no live recompute on input today, so the per-keystroke cost the audit was concerned about is not present.

## What shipped instead

A generic `debounce(fn, wait)` utility at `app.js` (just before `escapeHtml`). It's not wired to anything in v3.10.0 — it exists so future code that DOES add live search to the input handlers has a ready wrapper. Closing the finding without leaving the utility would force a re-discovery if/when the live-search pattern lands.

## Re-evaluate if

- A future change wires `findStrutCombinations` (or any expensive function) directly to `oninput` on measurement fields.
- Add the wrapper at that point: `oninput="debouncedFn()"` where `debouncedFn = debounce(actualHandler, 150)`.
